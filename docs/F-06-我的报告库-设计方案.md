## 一、结论摘要

**F-06 的实质不是"新增一个列表页"，而是修一个已经存在的缺陷：报告的唯一访问凭证是内存里的 `task_id`。**

`stock_detail.html:1220 / 1300 / 1623` 与 `sector_detail.html:481` **四处**都是 `frame.src = API_REPORT + '/' + taskId + '/html'`，而 `taskId` 只存在于 `TaskManager._tasks`（`api/tasks.py:17` 的进程内内存字典）。后果：

- **8002 服务一重启**，`GET /api/report/{task_id}` 立刻 404（`api/server.py:221-226`）；
- 磁盘上 `output/reports/.../report.html` **明明存在，却没有任何 URL 能打开它**；
- 连"当日复用"（`_reuse_today`，`api/server.py:73`）也救不了——复用分支同样要 `tm.create()` 造一个内存任务（`:205-211`）。

所以当前"生成过的报告"不是资产，是**一次性消耗品**。

F-06 要做两件事，缺一不可：

| 目标 | 内容 | 对应决策 |
|---|---|---|
| **主** | 给已落盘报告一个**与任务无关、与用户绑定**的稳定入口 | D1 / D2 / D3 |
| **辅** | 把它变成**按报告类型组织**的可浏览库 | 用户新增要求 |

技术核心因此是：**发明一个持久化且用户相对的报告标识（`report_id`），并让落盘、复用、扫描、打开四个环节在同一个用户维度上对齐。**

## 三、现状核清（事实清单）

### 3.1 落盘结构（`storage.py:25 report_output_path` / `:42 save_report`）

```
output/reports/{code}/[{report_type}/]{yyyymmdd}/   ← 基本面报告 type 段缺省
                  {code}/{report_type}/{yyyymmdd}/   ← overview / industry / board
```

| 类型 | 路径形态 | 段数 |
|---|---|---|
| 基本面（默认） | `output/reports/002594/20260922/` | **2 段** ⚠️ 与**实际写路径不符**（见 §15.5）：两条写路径都显式传 `report_type="fundamental"`，落盘恒为 3 段 `{code}/fundamental/{date}/` |
| 概况 / 行业 | `output/reports/002594/overview/20260922/` | 3 段 |
| 板块深度 | `output/reports/BK1036/board/20260922/` | 3 段 |

→ **扫描器必须同时处理 2 段与 3 段**。板块报告的第一级是 `BK\d+`，不是 6 位数字。

**⚠️ 两个函数都会自己重算目录**：`save_report`（`:55-61`）**不接收** `html_path` 的所在目录，而是用 `code/report_type/date` **重新拼一遍**再把 HTML 内容复制过去（`:64-65`）。这意味着任何路径改造**必须同时改这两个函数**，只改 `report_output_path` 会导致 HTML 与 `meta.json/profile.json` 分居两处。

### 3.2 报告类型清单（"按类型区分"的依据）

| key | 中文名 | 生成入口 | 标的主体 | 落盘段数 | 生成器 |
|---|---|---|---|---|---|
| `fundamental` | **基本面分析** | `stock_detail.html:286` | 6 位个股 | 2 段 | `main.run_pipeline` |
| `overview` | **公司概况** | `stock_detail.html:266` | 6 位个股 | 3 段 | `report_types/overview.py:4997` |
| `industry` | **行业对比** | `stock_detail.html:313` | 6 位个股 + 基准板块 `bk` | 3 段 | `report_types/industry.py` |
| `board` | **板块深度** | `sector_detail.html:146` | `BK\d+` 板块 | 3 段 | `report_types/board.py:745` |

中文名来源：各模板 `<title>`（`template.html:6` / `template_overview.html:6` / `template_industry.html:6` / `template_board.html:6`）。

**现状问题：这四个中文名散落在 6 处以上硬编码，没有单一事实源。** 前端按钮、模板标题、`schemas.py:18` 的注释各写各的。F-06 要建类型注册表，正好把它收敛（见 §7.1）。

### 3.3 `meta.json` 字段（实测，两类不一致）

| 报告类型 | 实测字段 |
|---|---|
| 个股（fundamental / overview / industry） | `code` `name` `report_type` `bk` `writer_mode` `search_used` `generated_at` `data_source` `validation` |
| 板块（board） | `bk` `name` `report_type` `generated_at` `data_source` `llm_ok` |

→ 三类不齐：board **无** `code`/`validation`，个股 **无** `llm_ok`；**两类都无 `user_id`、无 `bk_name`**。
→ 列表契约必须做归一化并给缺失字段兜底默认值，**不能直接透传 meta**。
→ `bk_name` 缺失影响"行业对比"列表项的可读性（只显示 `BK0890`）——`_worker`（`api/server.py:115`）的入参里**已经有** `bk_name`，落盘时补一行即可（见 §4.3-④）。

### 3.4 磁盘实况（2026-09-24 实测）

```
output/reports/002594/overview/20260922/{report.html, profile.json, meta.json}
output/reports/002594/overview/20260922_morning_noLLM/{report.html, profile.json, meta.json}
```

三点必须写进设计约束：

1. **总共只有 2 份报告、1 只股票**——功能价值现在体现为"止损"与"兑现既有设计红利"，而不是"管理大量存量"。
2. **`20260922_morning_noLLM` 不符合 `storage.py:36` 的 `%Y%m%d` 约定**（外部/早期脚本产物）→ **扫描器不能假设日期目录是 8 位纯数字**。
3. 同一 code + 同一天可能有多份（日期目录不同）→ 这既是 F-09 版本对比的天然素材，也意味着"当日复用"的索引必须**精确匹配目录名**，不能按前缀模糊命中。

### 3.5 同级目录污染风险

`output/` 下除 `reports/` 还有 `output/_probe/`（`all_in_one.sh` / `boot.log` / `boot2.log`，10 KB，**全仓无任何代码引用**，疑似运维残留）。
→ **扫描根必须是 `output/reports/`**，不能是 `output/`。

## 四、D1 定稿：报告归属与用户隔离

### 4.1 关键发现：只写 `user_id` 是**假隔离**

`report_output_path(code, report_type)`（`storage.py:25-39`）的路径只由 `code / report_type / date.today()` 三者决定，**不含任何用户维度**。于是：

1. 用户 A 今天生成 `600519` 的概况报告 → 写入 `output/reports/600519/overview/20260924/`，`meta.user_id = A`；
2. 用户 B 今天请求同一份 → `_reuse_today` 若按 `user_id` 判定"未命中"→ **重新生成 → 写入同一目录 → 覆盖 A 的报告**，`meta.user_id` 变成 B；
3. 结果：**A 的报告从磁盘上消失，也从报告库里消失**（两者的 `report_id` 完全相同）。

也就是说，**"按用户隔离复用"必须建立在"按用户隔离落盘"之上**。只往 meta 里加一个字段，会把"跨用户读到别人报告"（泄漏）换成"跨用户互相删报告"（数据丢失）——后者更难排查。

> 这条不是理论推演：它与本项目 2026-09-11 的"概况报告被基本面报告覆盖"事故**同型**——当时根因也是"去重/落盘键漏了一个维度"（漏 `report_type`）。

### 4.2 定稿布局

```
output/reports/u{user_id}/{code}/[{report_type}/]{yyyymmdd}/report.html
               └── 新增的用户段（仅当 user_id 非空时插入）
```

| 场景 | 定稿路径 |
|---|---|
| 用户 1 生成比亚迪概况 | `output/reports/u1/002594/overview/20260924/` |
| 用户 2 生成同一份 | `output/reports/u2/002594/overview/20260924/` ← **互不干扰** |
| 用户 1 生成板块报告 | `output/reports/u1/BK1036/board/20260924/` |
| 既有 2 份历史产物 | `output/reports/002594/overview/...` ← 无用户段 = **legacy 根**（见 D7） |
| CLI / 迁移脚本（`user_id=None`） | 保持旧路径（**向后兼容，既有测试的路径构造不变**） |

配套约定：

- `user_id` 为空 → **不插入用户段**，行为与今天完全一致。这让 `report_output_path` 的默认调用（及 `tests/test_reuse_by_mode.py:32` 的路径构造）**不被破坏**。
- 同理，`save_report` 也必须接收 `user_id`——**否则 meta/profile 会落到 legacy 目录，而 HTML 落到用户目录**（§3.1 的重算特性）。

### 4.3 连带必改清单（7 处，含 2 处测试）

| # | 位置 | 改动 | 不改的后果 |
|---|---|---|---|
| ① | `storage.py:25 report_output_path` | 新增 `user_id: int \| None = None`，非空时路径前缀 `u{user_id}` | 隔离无从谈起 |
| ② | `storage.py:42 save_report` | 同上新增 `user_id` | **HTML 与 meta 分居两个目录**（`:55-61` 重算路径） |
| ③ | `api/server.py:73 _reuse_today` | 新增 `user_id` 参数；路径按用户隔离；再以 `meta.user_id` **二次校验** | 复用判定与落盘路径不一致 |
| ④ | `api/server.py:115 _worker` | 线程入参加 `user_id`；`:130/:149` 两处 `report_output_path`、`:143/:173` 两处 `save_report` 全部传 `user_id`；两处 `meta` 增 `user_id`（board 分支亦然）；**顺带把已在入参里的 `bk_name` 写进个股 meta**（提升列表可读性，见 §3.3） | 落盘仍是公共路径；列表里 `industry` 只显示 `BK0890` |
| ⑤ | `api/server.py:182 create_report` | `user = _current_user(req)`（防御性 401，正常已被中间件拦住）；`user_id` 传给 `_reuse_today` 与 `_worker`；board 分支同样 | `/api/report` 是一个**没有任何身份信息**的入口 |
| ⑥ | `api/tasks.py:20 create` + `schemas.py:24 TaskStatus` | **`TaskManager.create` 的去重键加入 `user_id`**；`TaskStatus` 增 `user_id` 字段 | **两个用户同时生成同一只票会命中同一个 RUNNING 任务** → 状态与 `html_path` 互相覆盖（2026-09-11 事故同型复发） |
| ⑦ | `tests/test_reuse_by_mode.py` | `_reuse_today` 签名变化 → 用例改传 `user_id`；并**补一条 `user_id=None` 的 legacy 路径用例**锁定向后兼容 | 测试直接红，或向后兼容被无声破坏 |

> ⑥ 是最容易被漏掉的一条：v1 曾预估"改 3 处（`_worker` / `create_report` / `_reuse_today`）"，实际漏掉了**任务去重键**与**落盘路径本身**。

### 4.4 隔离的实现方式：路径隔离优先，meta 校验兜底

```mermaid
flowchart LR
  A["请求 /api/report/list"] --> B["8080 代理<br/>透传 Cookie"]
  B --> C["_current_user(req) → user_id"]
  C --> D["扫描根 = output/reports/u{user_id}/"]
  D --> E["report_id 解析基于本人根"]
  E --> F["view/{report_id}<br/>只在本人根内解析"]
```

**要点：`report_id` 不含 `user_id`，它是"用户相对"的标识。** 两个用户的同一份报告可以拥有**完全相同的 `report_id`**，但因为解析始终以"当前用户根"为基准，**越权在结构上不可能发生**（不需要额外的权限判断，也就不存在"忘了判断"的风险）。

`meta.user_id` 的角色是**对账与审计**（路径被手工搬动、迁移脚本误用时不至于静默错归属），不是权限的唯一依据。

## 五、数据模型：推荐"文件即索引"，不建索引表

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A（推荐）文件即索引** | 每次请求扫描用户根下的 `**/meta.json` 汇总 | 单一事实源，天然与磁盘一致；零新表、零迁移；与 `storage.py` 既有设计对齐 | 随报告数增长变慢；**无法承载"收藏/标签"等状态** |
| B SQLite 索引表 | 落盘时 INSERT 一行，列表查表 | 快；可承载状态 | **引入双写一致性问题**：落盘成功但 INSERT 失败 → 列表缺条目；文件被删但表还在 → 死链；需迁移与对账 |

**推荐 A**：

1. 项目既有哲学是"零迁移脚本"（`auth/db.py` 靠 `get_conn()` 每次幂等 `executescript`）。但那是**权威数据**（用户、自选）不得不入库；报告是**产物**，磁盘文件本身已是权威，再建一份索引等于人为制造两份真相。
2. 规模现实：现在 2 份。即便 1000 份，扫 1000 个约 500 B 的 `meta.json` 仍是毫秒级。
3. **升级路径已预留**：把扫描封成服务层函数 `list_reports(user_id, ...)`，将来量大换 SQLite **只改函数内部**，接口与调用方不变——与 `TaskManager` 注释里"换 Redis 对外接口不变"是同一套哲学。

> **D1 定稿对 A 的补强**：v1 曾把"无法记录归属"列为 A 的固有代价。定稿后**该代价由路径维度消化**（用户段），meta 冗余一份 `user_id` 用于对账——A 不再需要 B 来补归属能力。

## 六、接口设计（D2 定稿）

全部收在 `/api/report` 命名空间内（**关键收益：8000 侧零改动**）。

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/report/list?type=&code=&page=&page_size=&sort=` | 列出**当前用户**已落盘报告（跨标的的库视图） |
| `GET` | `/api/report/view/{report_id}` | 打开**当前用户**某份已落盘报告，返回 `text/html`（**不依赖 task**） |

### 6.1 「8000 侧零改动」的理由

`frontend/server.py` 的代理分支是 `parsed.path.startswith("/api/report")`（`:2371` GET、`:2465` POST），而 `_proxy_report()` 用 `self.path` **原样转发**（`:2409`）、并**原样透传请求头**（`:2415-2419`）。所以两个新端点天然被代理，且**会话 Cookie 会一起到达 8002**。

对照：F-03 因为选了新前缀 `/api/watchlist`，不得不在 8000 侧的 `do_GET`（`frontend/server.py:2363`）与 `do_POST`（`:2453`）各加显式分支。**命名放在既有前缀下，是这次能省掉四处改动的唯一原因。**

> 注：`startswith("/api/report")` 其实也能命中 `/api/reports`（复数），但那是"碰巧能通"，作为设计不应依赖 —— 这也正是 D2 选 ① 而不是 ② 的核心理由。

### 6.2 路由顺序护栏（必须显式保护）

- `GET /api/report/view/{report_id}` 与现有三个路由**都不冲突**，逐个核对：

  | 现有路由 | 段数 | 关系 |
  |---|---|---|
  | `GET /api/report/{task_id}`（`:220`） | 1 段 | 段数不同，不冲突 |
  | `GET /api/report/{task_id}/html`（`:228`） | 2 段 | 2 段相同，但**字面量位置不同**：它要求第 2 段为 `html`，本端点要求第 1 段为 `view`。唯一交集 `/api/report/view/html` 中，`html` 不是合法 `report_id`（三段校验会拒）→ **实际无冲突** |
  | `POST /api/report`（`:181`） | — | 方法不同 |

- `GET /api/report/list` 是**一段**，会被 `@app.get("/api/report/{task_id}")` 捕获 → 若注册顺序在后，`/api/report/list` 会返回 404「任务不存在」。

**约束**：`/api/report/list` **必须注册在 `:220` 之前**，两处各加中文注释说明原因，并用**一条测试锁定**。

**实测验证（2026-09-24，隔离 FastAPI 应用，未触碰项目代码）**：

| 注册顺序 | `GET /api/report/list` | `GET /api/report/view/{id}` | `GET /api/report/{task}/html` |
|---|---|---|---|
| `list` 在 `{task_id}` **之前** | **200** `{"ok":true,...}` | 200 ✓ | 404（任务不存在，符合预期） |
| `list` 在 `{task_id}` **之后** | **404 `{"detail":"任务不存在"}`** ← 被吞 | 200 ✓ | 404 |

结论：①顺序护栏**确有必要**，失效症状是"列表接口返回任务不存在"这种**极具误导性**的 404；②`view` 端点**两种顺序下都正常**，冲突分析成立，无需额外防护。

### 6.3 列表响应契约（归一化 + 类型注册表）

```jsonc
{
  "ok": true,
  "total": 5, "count": 2, "page": 1, "page_size": 20,
  "root_available": true,          // false = 用户根不可读（≠ 没有报告），见 §8.4
  "owner": { "user_id": 1, "scope": "personal" },

  // 类型注册表：**过滤前的全量计数**（否则筛选后 chip 计数全为 0，无法切回其他类型）
  "types": [
    { "key": "fundamental", "label": "基本面分析", "count": 1, "has_code": true  },
    { "key": "overview",    "label": "公司概况",   "count": 2, "has_code": true  },
    { "key": "industry",    "label": "行业对比",   "count": 1, "has_code": true  },

  ],

  "items": [{
    "report_id": "002594.overview.20260922",
    "report_type": "overview",
    "report_type_label": "公司概况",        // ← 前端不硬编码中文，直接用它
    "code": "002594",

    "bk": "", "bk_name": "",
    "generated_at": "2026-09-22 14:28",

    "llm_ok": null,                        // board 有值、个股为 null（字段不齐兜底）
    "validation_warnings": 0,
```

设计要点：

- **`types` 与 `items` 分离**：`types` 是全量镜像，`items` 是被过滤/分页后的结果。前端渲染筛选条与分区标题都取 `types`，**空类型不渲染分区**（沿用 F-02 的"空分组不占位"决策），无需前端自己数。

- **`subject_url` 由服务端算**：前端不做类型判断（board 无个股页）。**且只在标的主体合法时下发**——这堵住了 N-01 类"误跳转静默打开贵州茅台"的陷阱（`stock_detail.html:338` 的 `|| '600519'`）。
- **`view_url` 由服务端拼**：未来换 URL 形态前端不用改。
- 排序：`generated_at` 倒序；**`generated_at` 可能缺失**（外部产物）→ 用 `meta.generated_at or 目录 mtime` 兜底，**否则 `list.sort` 遇 `None` 会抛 `TypeError`**。

### 6.4 查询参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `type` | 空 | 过滤单一报告类型；空 = 全部（前端在"全部"模式下自行分区渲染）。**深链抓手**：`stock_detail.html` 三个面板的「查看历史报告」各自带自己的 `type` |
| `code` | 空 | 过滤单一标的（`\d{6}` 或 `BK\d+`） |
| `page` / `page_size` | `1` / `20` | `page_size` 钳制在 `1..100` |
| `sort` | `generated_at` | `generated_at`（倒序）/ `size`（倒序） |

## 七、`report_id` 与安全护栏

### 7.1 类型注册表（单一事实源）

新增于 `report_index.py`：

```python
REPORT_TYPES = {
    "fundamental": {"label": "基本面分析", "has_code": True},
    "overview":    {"label": "公司概况",   "has_code": True},
    "industry":    {"label": "行业对比",   "has_code": True},
    "board":       {"label": "板块深度",   "has_code": False},
}
REPORT_TYPE_ORDER = ["fundamental", "overview", "industry", "board"]
SUBJECT_PAGE = {"fundamental": "/stock_detail.html", "overview": "/stock_detail.html",
                "industry": "/stock_detail.html", "board": "/sector_detail.html"}
```

**未知类型的处理规则（重要）**：遇到不在注册表里的 `report_type`，**保留原值、`label` 用 key 本身、排在最后**，**绝不丢弃该条目**。理由与 N-07 的取向一致——宁可展示一个名字不好看的报告，也不能让它"凭空消失"。将来新增报告类型时，库不会因为注册表没同步而漏条目。

### 7.2 `report_id` 格式

`{code}.{report_type}.{date}` — 三段以 `.` 分隔（**不用原始相对路径**，含 `/` 会与路由段冲突且更易被穿越）。**不含 `user_id`**（用户相对，见 §4.4）。

| 场景 | report_id |
|---|---|
| 个股基本面（type 段缺省） | `002594.fundamental.20260922`（归一化补 `fundamental`） |
| 概况报告 | `002594.overview.20260922` |
| 非规范日期目录 | `002594.overview.20260922_morning_noLLM` |
| 板块深度报告 | `BK1036.board.20260922` |

### 7.3 目录段解析规则（按段数判定，不靠正则猜）

给定相对用户根 `output/reports/u{user_id}/` 的段序列：

| 段数 | 解释 | 产物 |
|---|---|---|
| 2 段 `[code, date]` | 基本面（type 缺省） | `type = "fundamental"` |
| 3 段 `[code, type, date]` | 其他类型 | `type = seg[1]`（可为未知类型） |
| 其他 | 非报告目录 | **跳过并记 warning，不猜** |

`date` 段**只校验非空与字符集**，**不做"必须 8 位数字"的假设**（§3.4-2 实测存在 `20260922_morning_noLLM`）。

### 7.4 三段白名单校验（逐段，缺一不可）

| 段 | 规则 |
|---|---|
| `code` | `^(\d{6}\|BK\d+)$`（复用既有 `_code_ok`（`:60`）与 `_bk_ok`（`:64`）） |
| `report_type` | `^[A-Za-z][A-Za-z0-9_]{0,31}$`（**不要求 ∈ 注册表**，与 §7.1 的"未知类型不丢弃"一致） |
| `date` | `^[A-Za-z0-9_\-]{4,32}$`（**不得含 `.`、`/`、`\`**） |

### 7.5 路径护栏

1. `Path.resolve()` 后断言仍在**该用户根**之内（`is_relative_to`）——注意是用户根，不是 `_DEFAULT_BASE`，否则越权检查落空；
2. `report.html` **必须存在**才返回，否则 404；
3. 任一环节不满足 → **一律 404，不回显拼接后的路径**（避免路径探测）。

## 八、前端设计：按报告类型组织（用户新增要求）

### 8.1 新增 `frontend/reports.html`

**照抄 `watchlist.html` 的骨架**（367 行，含内联脚本，与本项目"每页自带脚本、不引公用框架"的风格一致）。可复用的既有函数范式：

`esc()`（`:157`）／`toLogin()`（`:163`）／`showState()`（`:167`）／`renderEmpty()`（`:172`）／`renderUnavailable()`（`:182`）／`flash()`（`:251`）

其中 **`renderEmpty()` 与 `renderUnavailable()` 必须分开**（见 §8.4）。

### 8.2 类型区分方式定稿：**分区为主 + chips 筛选**

两种候选：

| 方式 | 优点 | 问题 |
|---|---|---|
| A 纯筛选（chips） | 省垂直空间 | 用户看不出"这个库有哪几类"，与"按类型区分"的诉求相悖 |
| B 纯分区（sections） | 类型差异一目了然 | 类型多时空区占位；无法快速聚焦单一类型 |
| **C 分区 + chips（推荐）** | 默认视图即"4 个类型分区"；chip 点击 = 聚焦/取消聚焦；**一套渲染逻辑**（服务端 `type` 参数供深链与减流） | — |

**定稿 C**，具体规则：

1. 顶部类型条：`全部 (5)` + 四类各自计数，**计数取 `types` 全量镜像**，任何筛选状态下数字都不变（否则切过去看到 0 会以为是空的）。
2. 分区标题：`报告类型中文名 + 计数`，按 `REPORT_TYPE_ORDER` 固定顺序。
3. **空类型不渲染分区**（沿用 F-02 决策）；`type` 筛选生效时只渲染一个分区。
4. 分区内按 `generated_at` 倒序。

### 8.3 列表项与**类型感知**的动作

每项统一呈现：类型徽标（4 色各一）· 名称 + 代码 · 生成时间 · 数据源 · 可信度标识（`llm_ok` / `validation_warnings`）· 「打开报告」。

**按类型不同的部分（这才是"区分"的实质）**：

| 类型 | 标的主体显示 | 次要动作（`subject_url` 有值才渲染） |
|---|---|---|
| 基本面分析 | `比亚迪 002594` | 查看个股详情 |
| 公司概况 | `比亚迪 002594` | 查看个股详情 |
| 行业对比 | `比亚迪 002594` · 基准板块 `BK0890 半导体` | 查看个股详情 |
| 板块深度 | `半导体 BK1036`（**无个股页**） | 前往板块页 |

- `industry` 的基准板块名依赖 §4.3-④ 补的 `meta.bk_name`；缺失时降级为只显示 `bk` 代号（不报错）。
- 板块行**不显示**"查看个股详情"，从结构上避免"点到不存在的东西"。

### 8.4 空态与不可用态必须分离（沿用 F-03 / N-07 的教训）

| 情形 | 服务端 | 前端文案 |
|---|---|---|
| 库为空（确实没生成过） | `ok: true, total: 0` | **"你还没有生成过报告"** + **按类型给出生成入口**：<br>· 基本面/概况/行业 → 「去个股页生成」（跳 `stock.html`）<br>· 板块深度 → 「去板块页生成」（跳 `sector.html`） |
| 用户根不可读（权限/路径异常） | `ok: false` / `root_available: false` | **"报告库暂不可用（这不是「没有报告」）"** |
| 单条 `meta.json` 缺失或损坏 | 跳过该条，其余正常返回 | 顶部闪现"有 1 份报告元信息损坏，已跳过" |

这条不是洁癖：本项目已发生过两次同类事故（股票页空列表、板块页"未找到匹配「」"），二次复发的代价远比多一个字段高。

### 8.5 打开方式（D3 定稿）

**新标签直接打开 `view_url`**（`target="_blank" rel="noopener"`）。

因为 `view` 用的是**持久化 id**，URL 可刷新、可收藏、可分享——这是相对现状的质变（现状连刷新都会 404）。列表内 iframe 预览留 v1.1（少一条 iframe 通信路径，也少一类高度/滚动适配问题）。

### 8.6 入口（三处）

1. **主导航**：`index.html:30-36` 的 `<nav class="nav-menu">` 内，"我的自选"之后插入 `<a href="reports.html">报告库</a>`。

## 九、D4 定稿：报告图表库本地化

### 9.1 做法：**内联**，而不是引用同源路径

两个候选：

| 方案 | 做法 | 问题 |
|---|---|---|
| A 改外链为 `/js/echarts.min.js` | 报告用根绝对路径引 8000 静态资源 | **只在应用内有效**：报告一旦被下载/发邮件/转 PDF（F-07），图表立刻空。且 8002 侧无静态服务 |
| **B 渲染时内联（推荐）** | 渲染阶段把库文件内容注入模板 `<script>` | 报告体积增加（见下） |

**定稿 B。** 理由：`storage.py:5` 已把 `report.html` 定义为"**可离线打印**"的产物；方案 A 恰好破坏了这句承诺，而且会把"报告能不能看"变成对运行时环境的隐式依赖——本项目已经两次栽在隐式依赖上（行情源、缓存）。

### 9.2 资源与体积

| 库 | 现状 | 定稿 |
|---|---|---|
| ECharts 5.5.0 | `frontend/js/echarts.min.js` **已存在**（1,029,248 B），已被 `stock_detail.html` 使用 | **复用它，不新增副本**（避免仓库里躺两份 1 MB） |
| Chart.js 4.4.1 | **仓库内无本地副本** | **新增** `frontend/js/chart.umd.min.js`（约 200 KB），与 ECharts 同目录同风格 |

体积影响（按实测推算）：

| 报告 | 当前 | 内联后 |
|---|---|---|
| 概况（Chart.js） | 69,975 B | 约 **270 KB** |
| 板块（ECharts） | 约 200 KB（含图表数据） | 约 **1.2 MB** |

可接受：报告是**交付物**（低频、一次性、需要可分发），不是页面资源（高频、需首屏速度）。

### 9.3 实施方式与降级

- 模板把 `<script src="https://...">` 改为 `<script>{{ chart_lib_inline | safe }}</script>`；
- 渲染函数（`overview.py:4997 render_overview`、`board.py:745 render_board`）读文件内容注入变量；
- **降级**：文件缺失/读取异常 → **回退 CDN 外链**（即现状行为），并在 `meta` 记 `chart_offline: false`；**绝不因静态资源缺失让报告生成失败**——与 `storage.py:10`"落盘失败绝不中断主流程"同一哲学；
- **交叉依赖需注释说明**：报告模块（`src/fundamental_agent/report_types/`）读 `frontend/js/` 是**刻意的跨模块引用**（为免 1 MB 重复），必须在代码处写明，否则下一个人会以为是路径写错。

## 十、必须守住的约束（实施 checklist）

1. **路由注册顺序**：`/api/report/list` 必须在 `/api/report/{task_id}`（`api/server.py:220`）之前，并有测试锁定。
2. **扫描根只能是 `output/reports/u{user_id}/`**（`user_id` 非空时），不得扫 `output/`（`_probe` 会被误收）。
3. **所有落盘路径必须经 `report_output_path`**：`save_report` 会**重算目录**，两处必须同时传 `user_id`。
4. **`TaskManager.create` 去重键必须含 `user_id`**（现有键：`code + bk + report_type`）。
5. **目录段数不定**：2 段 = 基本面（type 段缺省）、3 段 = 其他；其他段数跳过。**⚠️ 但基本面解析不能只认 2 段** —— 实际写路径恒为 3 段，读取侧必须**同时接受 2 段与 3 段**（§15.5 / N-21）。
6. **不假设日期目录是纯数字**（`20260922_morning_noLLM` 实测存在）。
7. **未知 `report_type` 不丢弃**（保留原值、label 用 key）。
8. **两类 meta 字段不齐**（board vs 个股）→ 服务层统一契约、缺失给默认值，不得透传 meta。
9. **`report_id` 三段白名单 + `resolve()` 后校验在"用户根"之内**（不是 `_DEFAULT_BASE`）；失败一律 404 且不回显路径。
10. **`generated_at` 排序要有兜底**（缺失时用目录 mtime），否则 `sort` 抛 `TypeError`。
11. **空态 / 不可用态 / 单条损坏 三者文案分离**（§8.4）。
12. **`types` 计数是过滤前的全量镜像**，与 `items` 不同源。
13. **`subject_url` 只在标的主体合法时下发**（`code` 必须来自扫描结果，禁止前端兜底默认值）。
14. **报告 HTML 生成不得因静态资源读数失败而失败**（§9.3 降级）。

## 十三、顺带发现（三个实质问题）

### 13.1 `_reuse_today` 不区分用户 → 跨用户报告泄漏（D1 已定稿修复）

`create_report` 调用 `_reuse_today(code, req.report_type, req.bk)`——**签名里没有 `user_id`**。命中时把"今天已生成的那份报告"直接交给当前请求者。

后果：用户 B 请求生成 `600519`，若用户 A 今天已生成过，**B 会原样拿到 A 的报告**（含 A 的数据口径与 AI 结论），且不消耗任何 LLM。

当前只有 admin 一个账号，所以**未暴露**；一旦开放注册就是真实的跨用户数据泄漏。D1 定稿后，该缺陷由"用户段路径 + 签名加 `user_id` + meta 二次校验"三处一并消除。

### 13.2 【新】行业对比报告：同日多基准会**互相覆盖**（D8）

`report_output_path(code, "industry")` 的路径是 `{code}/industry/{date}/`——**不含 `bk`**。而 `bk` 恰恰是行业对比报告的一个实质维度（`api/server.py:166` 的落盘注释也承认"industry 报告落盘绑定对比基准板块"）。

于是同一天先看"比亚迪 vs 半导体"、再看"比亚迪 vs 汽车整车"：
1. 第二次 `_reuse_today` 因 `meta.bk` 不匹配而**判定未命中**（`:96`，逻辑正确）；
2. 于是**重新生成**，写入**同一目录** → **第一份被覆盖删除**。

**这是与 §4.1 完全同型的数据覆盖缺陷**（键漏了一个维度），只是维度从 `user_id` 换成了 `bk`。F-06 把它暴露出来，因为报告库会显示"这里只有一份行业对比报告"。

**建议修法（成本 S）**：把 `bk` 并入日期段后缀 → `.../industry/{date}__{bk}/`。该形态与既有的非规范日期目录（`20260922_morning_noLLM`）同族，**段数不变**，扫描器无需改动；`_reuse_today` 改由路径天然命中。→ 见 **D8**。

### 13.3 文档与代码不符（N-11 同类，第三次）

`storage.py:3` 的 docstring 写 `output/reports/{code}/{yyyymmdd}/{report.html, profile.json, meta.json}`，而实际代码（`:33-36`）是 `{code}/[{report_type}/]{date}/`。建议本次一并更正为定稿后的布局说明（含 `u{user_id}` 段），避免下一轮排查再被误导。

## 附：本方案相对"原始设想"的四处修正

`docs/产品功能扩展建议清单.md` 里 F-06 的实现思路写的是"新增 `GET /api/reports?code=&type=&page=` + `reports.html` + `stock_detail.html` 历史版本时间轴"。核对代码后四处修正：

1. **接口命名**：`/api/reports` → **`/api/report/list` + `/api/report/view/{report_id}`**。理由：①落在既有 `/api/report` 前缀下可让 8000 侧代理零改动（F-03 的 `/api/watchlist` 吃了这个亏）；②原清单只提"列表接口"，**漏了"打开一份历史报告"这个更关键的接口**——没有它，列表点开还是死路。
2. **"我的"不是形容词，是工程量**：清单默认报告库天然是"我的"，但报告与任务**都不记录 `user_id`**，且落盘路径**不含用户维度**。D1 定稿后发现这不只是"加个字段"，而是**7 处连带改动**。
3. **清单低估了本项性质**：它写的是"让生成过的报告变成可持续浏览的资产"。核对后更准确的表述是——**它同时修掉一个现存缺陷（重启后已生成报告永久打不开）+ 一个现存泄漏（跨用户复用）+ 一个现存覆盖（行业报告同日多基准）**，这才是它应排在第二批首位的真正原因。
4. **漏了"按类型组织"这个产品维度**：原清单只把 `type` 当成一个查询参数。核对后发现四类报告在**标的类型、生成入口、页内动作**上都有实质差异（板块报告根本没有个股页），因此 v2 把类型提升为**列表的组织骨架**（分区 + 注册表 + 类型感知动作）。

### 15.5 补记（2026-09-26）：基本面报告在报告库里点开必 404 —— N-21

**现象**：从报告库点「力源信息 基本面分析报告」→ `{"detail":"报告不存在或不属于当前用户"}`（`GET /api/report/view/300184.fundamental.20260925`，8002 与 8000 代理两条路径都复现）。

**根因**：**设计里的"2 段约定"与实际写路径不符**，而读取侧是照着设计写的。

| 环节 | 实际行为 |
|---|---|
| 设计（本文件 §3.1 / §7.2 / §10 checklist 5） | 基本面报告 `report_type` 段**缺省** → **2 段** `{code}/{date}/` |
| 真实写路径（**唯一**一处） | `api/server.py::_worker` → `report_output_path(code, report_type=report_type, …)` + `storage.save_report(…, report_type=report_type)`，其中 `report_type` 来自 `schemas.ReportRequest.report_type`，**默认值就是 `"fundamental"`** → 非空 → **3 段** `{code}/fundamental/{date}/`（CLI `main.py --type` 默认值同样是 `"fundamental"`，且 CLI 走 `--out`，根本不落报告库） |
| 列表（`list_reports` → `_build_item`） | 按**实际目录段数**反解 → 3 段 → `report_type="fundamental"` → `report_id = 300184.fundamental.20260925` ✅ 正确 |
| 打开（`resolve_report_html` → `report_dir`） | 按"fundamental 即 2 段"反推 → 找 `u1/300184/20260925/report.html` ❌ **实际不存在** → 404 |

即 **列表广告了 view 结构性拒绝的条目**：报告库里**所有**基本面报告都点不开（不限于力源信息、不限于该用户）。2 段形态在本机磁盘上**一份都不存在**。

**为什么长期没被发现**：`tests/test_report_index.py::test_report_id_roundtrip` 已经写了这条不变量（"列表里出现的每一条都必须能被 view 反解，否则就是「点开就 404」的死条目"）——但它**只抽查了 `overview`**（类型段恒非空 → 永远走 3 段），而"2 段归一路径"的用例是**用 `report_type=""` 人工造出来的**，造的正是现实中不存在、而读取侧唯一认识的那种形态。**测试锁定了错误的约定**。

**修复**（`report_index.py`）：

- 新增 `report_dir_candidates(user_id, code, report_type, date_seg)` → 基本面返回 `[{code}/fundamental/{date}, {code}/{date}]`，非基本面返回单候选；`report_dir()` 退化为"首选候选"。
- `resolve_report_html()` 改为**逐个候选**做原有三条护栏（三段白名单 → `resolve()` 后仍在用户根内 → `report.html` 真实存在），命中即返回。**越权与路径穿越的语义不变**。
- 优先级：3 段在前（当前写路径的形态）；两种形态同时存在时取更具体的那份。

**新增回归用例（`tests/test_report_index.py`，+4 例 → 40 例）**：

| 用例 | 锁定的东西 |
|---|---|
| `test_three_segment_fundamental_is_openable` | 直接重现本次故障（写路径的真实形态必须可打开） |
| `test_two_segment_fundamental_still_resolves` | 2 段向后兼容不被"顺手删掉" |
| `test_fundamental_prefers_explicit_type_segment_when_both_exist` | 优先级 |
| `test_every_listed_item_is_openable_across_all_layouts` | **类级护栏**：2 段/3 段基本面、overview、industry（D8 后缀）、board 五种形态**逐条**断言可打开。新增类型/新形态时把它加进这一条即可 |

**端到端验收**（临时会话，验完即删）：8002 直连 `200 / 115,252 字节 / 含"力源信息"`；经 8000 代理同样 `200`；列表 4 条的 `view_url` 全部 `200`；不存在的 `report_id` → `404`；路径穿越 → `404`；无会话 → `401`。

**教训（新，与既有纪律同族）**：

1. **「签名默认值」≠「调用方实际传参」**。`report_output_path(report_type="")` 的默认值确实是空串，但**没有任何调用方用它**。设计文档读的是函数签名，实现节奏照着签名走 —— 这是「实现了一条路径 ≠ 验证了这条路径真的在跑」的**镜像版本**：这边是「基于默认值设计了一条路径 ≠ 调用方真的走它」。
2. **不变量写了断言，不等于覆盖了**。`"列表里每一条都能打开"` 是**类级**不变量，抽查一种形态等于没查。类级不变量必须**遍历全部形态**（本文件新增的第四个用例就是它）。
3. **写侧/读侧对同一约定的理解必须由磁盘产物对齐**：判据是「磁盘上真实存在哪种形态」，不是「文档里写的是哪种」。修完顺手扫了一遍真实落盘——`output/reports/**` 全是 3 段，无一份 2 段。
