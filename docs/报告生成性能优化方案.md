# 报告生成性能优化方案

> 适用范围：公司基本面报告（fundamental）/ 公司概况报告（overview）/ 行业对比报告（industry）
> 定位日期：2026-09-06　状态：**短期措施 #1-#5 已实施（2026-09-06 晚）**；长期方向 #6-#10 待排期；**概况报告专项 OV-1~OV-7 已全部实施（2026-09-08~09，实施记录见 6.5）**

## 一、主要性能瓶颈定位（结论速览）

1. **三类型共用 pipeline 全量前置**：`run_pipeline` 串行执行「财报 → 概况六层取数（含年报 PDF 下载解析）→ 六大分析引擎」后才进入各类型专属阶段；行业对比报告实际只需要定量指标 + 公司画像，却被迫跑完全套（实测 22% "拉取概况数据"阶段卡约 2 分钟，全属无效前置）。
2. **概况六层取数全部串行**：cninfo / 股东 / 分红 / 新闻 / 主营 / 质押等接口相互独立，却在 `main.py` 中逐个串行 try 调用。
3. **LLM 调用档位浪费**：max_tokens 阶梯从 6000 起步，而 qwen 对 6000 必报 402（按预留额度计费），每次都白等一轮完整失败再降档；重试 2 次进一步放大延迟。
4. **无产物级复用**：同股同类型同板块当日重复生成时全量重跑，缓存只覆盖底层数据接口。
5. **并发能力受限**：pipeline 在 uvicorn 进程内以线程运行（GIL + py_mini_racer 线程安全隐患），画像取数只能串行保险；六大引擎中占位实现也空转计入耗时。

## 二、短期措施（可快速落地）

按预期收益 ÷ 实施难度排序：

| # | 方案 | 针对 | 预期提升 | 实施成本 |
|---|------|------|---------|---------|
| 1 | **行业对比报告跳过六大引擎 + 年报 PDF 下载解析**，仅取定量指标与公司画像 | industry | 约 3~4 分钟 → 1 分钟内 | 低：industry 分支旁路约 20 行 |
| 2 | **概况六层取数并行化**：独立接口改 ThreadPoolExecutor 6 并发 | overview（industry 回退路径同步受益） | 22% 阶段 2 分钟 → 约 30 秒 | 低：半天内 |
| 3 | **LLM 调用参数修正**：max_tokens 直接从 4000 起步；重试从 2 次降为 1 次 | 三类型的 AI 内容环节（industry 最重） | LLM 阶段省 30~60 秒/次 | 极低：改一个元组 |
| 4 | **同股同日产物复用**：同 code+type+bk 当日已有 SUCCESS 报告时直接返回路径 | 三类型重复生成 | 重复请求秒回 | 低：TaskManager 加一层查询 |
| 5 | **占位引擎跳过**：六引擎中占位实现直接跳过 | fundamental | 数秒~十几秒 | 极低 |

预期综合效果：industry **约 3~4 分钟 → 40~70 秒**；overview / fundamental **提速约 40~60%**。

#### 线程安全专项（措施2 前置，2026-09-06 复现）

- akshare 的 cninfo 系接口（`stock_dividend_cninfo` / `stock_profile_cninfo`）每次调用用 py_mini_racer
  新建 V8 isolate；**多线程并发会触发 V8 FATAL，进程以 exit code 3 静默崩溃**（栈顶 mini_racer.dll）。
  崩溃具偶发性（同组合有时存活），不可赌概率。本次实测：industry 画像 6 路并发（`_gather_profiles_parallel`
  调 `stock_profile_cninfo`）直接复现崩溃 → 已修复。
- 修复：`data/cninfo_guard.py` 提供进程内唯一可重入锁，akshare.py 的 `get_dividend` / `get_identity`
  的 cninfo 段、industry.py 的 `fetch_company_profile` 的 cninfo 段全部包进锁；HTTP 类接口（东财/申万）
  不受锁约束自由并行。
- 并发探针（`serialCtl/control/http6/phaseA/lockA` 五模式子进程）全部存活；方案采用 lockA 形态
  （HTTP 池 + cninfo 持锁并行）。
- 另修复 main.py 一处潜在 NameError：年报公司行动抽取异常分支引用 `logger` 但模块从未定义。

#### 措施4 说明

- 复用键 = code + report_type + bk（industry 按板块基准精确匹配，历史无 bk 字段的旧产物仅在请求
  bk 为空时命中）；当日路径天然含日期，无需额外日期校验。
- 「重新生成报告」按钮语义保留：前端点击时若按钮文本为「重新生成报告」则请求带 `force:true`，
  后端跳过复用直接重跑。

### 6.2 新增优化点清单（按 收益÷成本 排序）

| # | 优化点 | 具体思路 | 预期效果 | 实施难度 | 优先级 |
|---|--------|---------|---------|---------|--------|
| OV-1 | **砍掉概况路径的 summarize_analysis** | main.py `if use_llm:` 分支加 report_type 判断，仅 fundamental 执行润色与总结；overview 的 AI 结论已由主生成提供 | 省 10~30s + 一次 API 费用，零功能风险 | 极低（1 行） | ★★★ 当天 |
| OV-2 | **get_holders 治理** | 三选一或组合：(a) 顺序反转——优先用已抽取的股东名册（report_holders）作前十大来源，get_holders 降为名册缺失时兜底（名册本就是监管披露口径、代码注释已认定更优）；(b) 按 (code, 报告期) 当日缓存；(c) 全市场大表一次拉取后按代码切片复用，杜绝最多 6 次全量请求 | 概况数据阶段 60s → 约 20s | 低（(a)/(b)）、中（(c)） | ★★★ 当天 |
| OV-3 | **LLM provider 熔断** | 仿 ROE 备源熔断范式：某厂商连续 N 次失败（402/超时）后当日跳过，不再每次调用都付一次必败往返 | 每次 LLM 调用省一次失败往返；限流/欠费场景整体提速 | 低 | ★★★ 当天 |
| OV-4 | **主生成重试降档** | generate_overview_content max_retries 3 → 1~2；进一步改为「重试仅补写 conclusion_html 字段」而非整份 8000 token 重生成（保留其余已验证字段） | 最坏情况（连续空结论）省 1~2 分钟 | 低（降档）、中（局部补写） | ★★☆ 一周内 |
| OV-5 | **LLM 子调用并行化** | biz_enrich / growth 聚焦 / 主生成三者独立，ThreadPoolExecutor 并行发起（主生成输入不含两者输出，需先核确认；若确认有依赖则并行前两者） | LLM 阶段省 20~60s | 中（router 线程安全需确认） | ★★☆ 一周内 |
| OV-6 | **收紧六层并发池预算** | _POOL_BUDGET_S 180s 过宽，单层挂起会拖满；配合 OV-2 后实际 max(jobs)≈9s，收紧至 60s | 尾延迟可控，不被单层拖死 | 低 | ★★☆ 当天 |
| OV-7 | **削减主生成输出量** | 确定性表格字段（分红/股东/主营等）全部由数据层提供，LLM 仅写叙事与结论层，生成 token 减半（8000 → 预期 4000 级） | 主生成 30~90s → 20~50s | 中高（六层契约改动，需完整回归） | ★★☆ 中期 |

**与既有条目的关系**：流式输出（感知延迟）= 长期项 **#10**；cninfo/MiniRacer 替换 = 长期项 **#8**；数据快照预取 = 长期项 **#6**——本章不重复立项。gzip / K线式降采样对概况报告不适用（payload 小、字段结构化）。

**实测总结**：no-LLM 数据层端到端 **66.4s → 21~25s**（-62%~68%）；叠加 LLM 层收益（OV-1 少一次调用、OV-3 少必败往返、OV-4 重试上限降档、OV-5 子调用并行），概况报告整体预期从 2~4.5 分钟降至 **1~1.5 分钟内**（LLM 真实耗时待额度恢复后校准）。

#### 进程崩溃专项（OV-2 实施中发现的既有不稳定）

- **现象**：六层并发池运行中进程偶发**静默退出（exit 0、无 traceback、faulthandler 无输出）**。单任务隔离全部正常，仅多任务并发组合触发；与 fitz/MiniRacer 加载顺序无关（新旧代码、两种顺序均可复现；二分定位非 cninfo 系（纯 HTTP 系）并发组亦会触发）。
- **性质**：akshare C 扩展层（lxml/MiniRacer 等）在 GIL 高并发下的环境级不稳定，属既有问题（文档 2026-09-06 已记录 V8 FATAL 前科），非 OV 系列改动引入。
- **处置**：六层取数整体迁入 **spawn 子进程**（daemon + Pipe 回传）——子进程崩溃不再波及 uvicorn 服务与报告任务；父进程重试一次，两层全失败按「单层失败回退空值」语义降级继续。
- **注意**：spawn 要求可导入的 `__main__`——`python -m fundamental_agent.main` 与 uvicorn 均满足；以 `python -`（stdin）方式运行会优雅降级（告警 + 空层）并重试后继续，不影响真实部署路径。
- **残留风险**：崩溃根因仍在 akshare 扩展层，根治需长期项 #8（cninfo/MiniRacer 替换为纯 HTTP）与 #9（worker 进程池）；当前隔离方案保证业务连续性。

#### OV-6 预算回归与修复（2026-09-09）——「股权治理/行业坐标为空」的根因

**回归现象**：用户报告概况报告「股权治理」「行业坐标」区块数据为空。实证（688981 中芯国际，20260909 产物）：
`holders=0 / dividend=0 / pledge=0 / peers=0`，而 identity/segments/share_capital/market 正常。

**根因**：OV-6 把六层池预算 180s→60s 过紧（直接调用 `_overview_layers_worker` 复现：688981 耗时 **61.1s** 撞上 60s 预算），
且 worker 的超时语义为 `as_completed(timeout)` 抛错后 `shutdown(cancel_futures=True)` —— **把所有未完成的层整体取消丢弃**，
不是「只丢慢层」。慢层（dividend 走 cninfo 全局锁、pledge、peers 申万二级重取数、holders 全市场大表 39s）超时即连带全灭。
加剧因素：holders 补取兜底以「跳过 get_holders」为前置条件，未走跳过分支时永不触发；`_safe_records` 把异常与真空一律吞成 `[]`，空值不可归因。

**修复（2026-09-09 落地）**：
1. **超时语义改造**：`as_completed(timeout)` → `wait(futs, timeout)` 收集已完成层，超时层仅标记 `timeout`，不再牵连其它层；整体预算 60→120s。
2. **holders 独立通道**：从六层池剥离，单独单线程 + 45s 独立超时，与池并行、不共享预算；并且**不再按「PDF 缓存存在」跳过**（原判定有洞：缓存存在 ≠ 名册抽得出来，688981 即缓存有 PDF 但名册 <5 行 → holders 双向落空）。
3. **兜底解耦**：父进程 holders 补取条件由「跳过过才补」改为「holders 为空即补」。
4. **层状态可观测**：worker 回传 `status: {层: ok|empty|timeout|error}`，父进程逐层打日志；`_safe_records` 异常记入 status（空值可归因：「上游真空」与「失败/超时」不再混淆）。
5. **get_holders 候选期 6→3**（每次拉全市场大表 5-10s，6 期逐次拉实测 39s；holders 仅为名册缺失时的兜底口径，3 期足够）。

**验证**：688981 worker 复跑 9 层全部回传（dividend/pledge 确认为上游真空——该公司确无分红/质押记录，status=empty 可归因）、peers=8、holders=10；端到端 no-LLM：688981 110.9s（其上游本就慢）、300184 32.5s（各层 ok，无串行补取）。

**同期修复「三年分部趋势只取一期」**（`overview.py`，独立缺陷）：
- 产品名基准从「最新一期」改锚「最近一期年报」（半年报分类名目更细，以它为基准会把全部年报期整期判死，实测 300308 仅剩 2026H1）；
- 期次采纳从 `all()` 全等匹配改为「匹配率 ≥70%」，并新增**前缀包含规则**（同一产品简称/全称漂移，如「光通信收发模块」vs「光通信收发模块及器件」，关键词交集为 0 被判死）；
- 最少期数校验移到过滤**之后**：`_ok_dates < 2` 时整块隐藏，杜绝单期假趋势；剔除原因逐期打日志。
- 验证：300308 `2025、2026H1`（真 2 期）、600941 恢复 4 期（2025 年报回归）、601288 无回归。

**渲染层空态提示**（`template_overview.html`）：「分红与股东回报」「治理风险扫描」在数据缺失时显示「未获取…」而非空标题；行业坐标在无可比公司/无行业定位时显示对应提示，替代整段留白。

## 七、基本面报告速度优化（FV 专项，2026-09-10~11 落地）

> 用户反馈：基本面报告「每次生成都慢」（含同公司重复生成）。用户确认取舍：LLM 仅并行+超时分级；数据缓存全部加上。

### 7.1 耗时构成与根因（实测）

| 阶段 | 优化前 | 根因 |
|---|---|---|
| 六层取数子进程（共用 overview worker） | **300-420s 且经常超时丢层** | peers 层：`sw_l1_map` 缓存长期只有 2843 条 < 代码阈值 4000 条 → **每次调用触发全量重建**（5000+ 只 / 90s 上限，peers 内另有无超时重建实测 624s）；申万成分接口故障时 3 次重试再叠加 |
| build_statements（财报） | 首跑 20-40s（7 天缓存） | 与六层取数串行（数据源独立，纯白等）；同业循环逐股 `get_financial_indicators`+`get_company_profile` 均无缓存 |
| 年报 PDF 抽取 ×3 | 每次重新解析同一 PDF | 解析结果未缓存 |
| LLM ×2（fundamental 特有） | 串行 20-60s；故障最坏 ~30min | 两调用输入互不依赖却串行；单请求默认 600s |
