# TradeAI 项目全面审视与优化清单

> 审视日期：2026-09-23　审视范围：全仓（141 个 git 跟踪文件 / 2.27 万行 Python / 7.6 千行前端）
> 性质：**只分析、不修改代码**。优先级：P0 阻断（安全/数据事故）→ P1 高 → P2 中 → P3 低/择机。

---

## 0. 事实基线（审视起点）

| 项 | 实况 |
|---|---|
| 技术栈 | Python 3.13 + FastAPI/uvicorn(8002) + 手写 `ThreadingHTTPServer` 静态服务(8000) + vanilla HTML/ECharts（无构建、无 npm） |
| 数据源 | AkShare + 东方财富 push2/push2delay + 巨潮 cninfo + 年报 PDF（PyMuPDF） |
| LLM | 多厂商 OpenAI 兼容路由（qwen → deepseek → zhipu），密钥经 `.env`，含「当日熔断」 |
| 报告类型 | 4 类：基本面 / 公司概况 / 行业对比 / 板块深度，产物按 `output/reports/{code}/{type}/{date}/` 物理隔离 |
| 认证 | 账号密码（scrypt）+ 会话 Cookie（HttpOnly/SameSite=Lax）+ 图形验证码（注册/找回） |
| 数据规模 | 数据缓存 14MB（年报 PDF 37.7MB 口径已随缓存清理）、`stocks.json` 5MB、`.venv` 374MB |
| 文档 | `docs/` 5 篇（方案 / 实施记录 / 事故复盘 / 缓存策略 / 性能优化），质量高、粒度细 |
| 测试 | 11 个 `test_*.py`（pytest）+ 18 个 `verify_*/audit_*/repatch_*` 手工脚本；**pytest 未列入依赖，开箱跑不起来** |
| CI / Lint | 无 `.github/`、无 ruff/mypy/flake8 配置 |

**先说做得好的地方**（这些是资产，优化时不要破坏）：

1. **护栏体系**：`overview.py` 里的事实核对表、持股硬错误正则、数字量级证伪（0.55x~1.8x 带）、存货/应收错标专项、`_strip_segment_margins` 数据级根治口径混用——这是本仓最有价值的部分，属同类项目里罕见的严谨度。
2. **降级不中断**的文化：LLM 挂了走 fallback 文本、单层取数失败回退空值、writer 直写失败回落 contract，且**绝不产空壳**。
3. **事故留痕习惯**：`docs/报告任务状态管理.md` 的 task 串扰复盘堪称范式（现象 → 机制链 → 插桩证据 → 修复 → 验证）。
4. **性能优化有基线**：66.4s → 21~25s 这类「前后对比 + 复跑探针」的实证方式非常专业。

## 二、产品经理视角

关注：功能完整性、用户体验、需求合理性、市场价值与迭代优先级。

### A. 功能完整性

| 编号 | 优化点 | 优先级 | 简要理由 |
|---|---|---|---|
| P-01 | **首页三张功能卡片点击无反应**：`main.js` 中三处 `window.location.href` 全被注释掉，只剩 `console.log` | **P0** | 首屏最大三个 CTA 是死的；用户唯一入口只剩导航栏两项。属于「打开就能发现」的硬伤 |
| P-02 | **首次登录强制绑定手机号未实现**：`sms.py` 不存在，`sms_codes` 表建了但空置；`AUTH_*` 方案阶段 1 只完成一半 | P1 | 注册即「手机号=用户名且视为已绑定」，等于**跳过短信验证**——绑定环节形同虚设，与文档宣称的能力不一致 |
| P-03 | **无报告历史/归档入口**：当日复用（措施 4）后端已实现，前端完全无 UI | P1 | 用户刷新页面后找不到刚生成的报告；后端已具备的「秒回」能力被浪费 |
| P-04 | **无导出/下载/分享**：报告只在 iframe 内预览，无 PDF、无下载按钮、无分享链接 | P1 | 「可下载的 HTML 报告」是产品宣称卖点（首页文案 + README），实际未落地。这是从「玩具」到「可交付物」的关键差 |
| P-05 | **生成过程是黑盒等待**：有 stage/百分比，但无预计剩余时长、无取消、失败后无「重试」按钮（只能再点一次） | P2 | 单份报告 1~4 分钟的等待里，用户没有控制感；失败时状态是 FAILED 但前端引导不明 |
| P-06 | **无用户中心 / 自选股 / 关注板块** | P2 | 报告生成是重成本操作，没有「我关注的公司」就没有留存钩子，每次都要重新搜代码 |
| P-07 | **页脚「使用条款 / 隐私政策 / 联系我们」全为 `href="#"`** | P1 | 一个收集手机号的产品，无隐私政策是**实质合规缺口**（非形式问题） |
| P-08 | **免责声明只出现在生成的报告内**，站点本身无风险提示 | P1 | 金融信息类产品需在入口处声明「不构成投资建议」；目前首页/个股页均无 |
| P-09 | 无跨市场/全站搜索入口：首页没有搜索框，必须先进个股页 | P2 | 最常见的首批用户动作是「搜我的股票」，被推迟两步 |
| P-10 | PWA 未落地：无 `manifest.json`、无 service worker（方案阶段 3 未启动） | P3 | 文档论证过的「零成本 App 化」路径，属低成本高感知项，可择机 |
| P-11 | 无使用引导 / 示例标的：首次进入不知道该输什么代码 | P2 | 降低首次成功率；一行「试试 600519 / 300184」即可解决 |
| P-12 | **数据时效性口径未在 UI 显式标注**：行情走 `push2delay`（延时行情），报告内标了快照日期，但前端行情区无「延时」标识 | P1 | 金融产品把延时数据当实时展示是**误导性风险**，需明示 |
| P-13 | `stepper.html` 是组件 demo 页，无任何页面引用，混在产品站点里可被直接访问 | P3 | 应移入 `frontend/dev/` 或删除，避免对用户暴露内部草稿 |

### A. 安全与合规（架构前置，全部最高优先）

### D. 性能

| 编号 | 优化点 | 优先级 | 简要理由 / 证据 |
|---|---|---|---|
| **T-30** | **「拉取失败被当成真空并缓存」——你实际踩到的股票页空列表** | **P0** | `fetch_stocks.py::fetch_all` 每页失败 3 次即 `break`，最终返回 `[]`（`rows` 空），**不抛异常**；`server.py::get_records` 视为成功，把 `[]` 连同当日日期写入缓存 → **整日不可自愈**，重启无效。修法：区分「失败」与「真空」，失败不写缓存 |
| **T-31** | **每个受保护页面请求都同步调用一次 8002 `/api/auth/me`**（timeout 3s） | P1 | `frontend/server.py:1555-1572`。页面 TTFB 被加一次内网往返；后端未启动时每页等满 3s。可改为本地会话缓存（如 5~10s TTL）或本地验签 |
| **T-32** | **外部取数大量走 `subprocess.check_output(["curl", ...])`** | P1 | `frontend/server.py:189`、`fetch_stocks.py:63`。每次请求 fork 一个进程，Windows 上进程创建成本高；已声明 `httpx` 依赖却未用。应改 httpx（保留 curl 仅作最后兜底） |
| **T-33** | **全市场 5000+ 条每次请求全量内存排序/过滤**，`stocks.json` 5MB 未压缩 | P2 | `handle_api_stocks` 对全量 recs 排序后再切片；关键词搜索也走全量。可预建索引或改服务端排序（板块路径已这么做，个股路径可对齐） |
| **T-34** | **LLM 长 JSON 契约 + 重试仍是 P95 主要成本**：概况主生成 8000 tokens，空结论时 2×8000+1×1200 | P2 | OV-4/OV-7 已优化，但未上流式（长期项 #10）。用户感知延迟仍以「分钟」计 |
| **T-35** | **并发能力受限于进程内线程 + GIL**：六层取数已子进程化，但财报拉取、引擎、LLM 仍在 uvicorn 进程内 | P2 | 三类型并发提交时互相拖慢；与 T-14 同源（长期项 #9） |
| **T-36** | 前端无资源压缩与缓存策略：仅 HTML `no-store`，`echarts.min.js` 1MB 每次弱网重下 | P3 | 无 Nginx/gzip；上线云端前建议由反代补 gzip + 长缓存 |
| **T-37** | `data/auth.db` 每次 `get_conn()` 都 `executescript(SCHEMA_SQL)` + `PRAGMA` | P3 | `auth/db.py:88-97`。设计上幂等，但每请求执行 DDL 有额外开销；应只在进程启动时建表 |
