## 一、目标与范围

### 1.1 目标

把已经存在但**完全无效**的"加自选"入口变成真实、可持久化的用户资产。

当前状态（证据）：

| 现状 | 位置 | 问题 |
|---|---|---|
| 按钮只切换自身文案 | `stock_detail.html:179` 定义、`:1108` 实现 | `textContent` 在"加自选/已自选"间切换，**不落库、不发请求，刷新即丢** |
| 列表页无自选概念 | `stock.html:254-281` 的 `buildRow()` | 无星标列、无"仅看自选"筛选 |
| 首页无入口 | `index.html:30-35` 主导航仅 4 项 | 用户无处查看自己的自选 |

**业务目标**：建立"用户 → 关注标的集合"这层关系。它是产品从"一次性查询工具"转向"日常陪伴"的**唯一地基**——没有自选，后续的日报、提醒、订阅、组合对比都无处附着。

**成功判据**：用户加自选后关闭浏览器，隔天回来（或换设备）仍能看到；且列表页可直接只看自选。

### 1.2 范围内（v1）

1. 自选的**增 / 删 / 查**（单用户私有）。
2. `stock_detail.html` 按钮真实化：进入页面回显"已自选"状态，点击可加可取消。
3. 自选列表页：展示自选标的的行情（复用全市场行情缓存，见 §4.3）。
4. `stock.html` 列表新增"仅看自选"筛选与星标列。
5. 空态与行情异常态的明确区分。
6. 首页/导航入口。

### 1.3 范围外（明确不做，避免范围蔓延）

| 不做 | 归属 |
|---|---|
| 分组 / 标签 / 备注编辑 | F-03 v2 |
| 拖拽排序、批量导入导出 | F-03 v2 |

## 二、主要模块与组件划分

### 2.1 关于"API 放哪一侧"的关键决策

系统存在两个进程，能力互补，**必须分清职责**：

| 进程 | 端口 | 具备能力 | 缺少能力 |
|---|---|---|---|
| 静态服务 `frontend/server.py` | 8000 | **全部行情取数**（`/api/stocks`、`/api/stock`、`/api/kline`、`/api/boards*`、`/api/news`）、同源代理、页面路由拦截 | **不碰数据库**（会话校验靠 HTTP 回调 8002，见 `:1555-1572`） |
| FastAPI `api/server.py` | 8002 | **数据库**（`auth.db`）、用户身份（`auth_service`）、报告 pipeline、全局鉴权中间件 | **无任何行情取数能力** |

**决策：自选 CRUD 放 FastAPI（8002），行情富化放静态服务（8000）。**

理由：
- 用户身份与 `auth.db` 只在 8002；`get_conn()`（`auth/db.py:88-97`）**每次连接都执行 `executescript(SCHEMA_SQL)`**，新增表天然幂等、**零迁移脚本**。
- 8002 的 `_auth_gate` 中间件（`api/server.py:263-270`）已自动保护所有 `/api/*`（`/api/auth/*` 除外）→ 新增 `/api/watchlist` **无需改动任何鉴权逻辑**。
- 行情取数全部在 8000，且 8000 已具备代理 8002 的能力（`_proxy_report`，`:1703`），反向不成立。
- **单一写入方原则**：只有 8002 写 `auth.db`，避免 SQLite 多进程写竞争（库已开 WAL，但没必要引入竞争）。

### 2.2 组件划分

| 层 | 组件 | 载体 | 改动性质 |
|---|---|---|---|
| L1 数据层 | `watchlist` 表 + 索引 | `auth/db.py` 的 `SCHEMA_SQL` | 追加（幂等建表） |
| L2 领域层 | 自选仓储函数：`list_by_user` / `add` / `remove` / `reorder` | `auth/` 下新增（建议独立 `watchlist.py`，与 `service.py` 平级） | 新增 |
| L3 接口层 | 4 个端点 + 请求/响应模型 | `api/server.py` + `api/schemas.py` | 新增 |
| L4 网关层 | `/api/watchlist` 代理分支 + `/api/watchlist_quotes` 行情拼装 | `frontend/server.py` 的 `do_GET` / `do_POST` | 新增分支 |
| L5 页面层 | 按钮真实化 | `stock_detail.html` | 改 1 处假实现 |
| L5 页面层 | 自选列表页 | 新增 `watchlist.html`（方案 A）或 `stock.html` 加筛选开关（方案 B） | 新增/改 |
| L5 页面层 | 入口 | `index.html` 导航 | 新增 1 项 |
| L5 页面层 | 状态保持 | `js/list_state.js` 快照字段 | 扩 1 个字段 |

**方案 A / B 选择建议**：优先 **A（独立 `watchlist.html`）**。理由：`stock.html` 已承载服务端分页 + 兜底渲染双路径（`renderApi` / `doFallbackRender`），再叠加自选筛选会显著抬高复杂度；独立页面可完全复用 `stock.html` 的行渲染与列表样式，且后续 F-23/F-24 的"自选中心"有自然落点。**B 可作为 A 的后续增强**（在 A 稳定后，再把"仅看自选"开关加进 `stock.html`）。

## 三、关键数据结构与接口设计

### 3.1 表结构（追加进 `auth/db.py::SCHEMA_SQL`，`:44-81`）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | INTEGER PK AUTOINCREMENT | |
| `user_id` | INTEGER NOT NULL | `REFERENCES users(id) ON DELETE CASCADE` |
| `code` | TEXT NOT NULL | 6 位纯数字股票代码，与 `_code_ok()`（`api/server.py:52`）同口径 |
| `name` | TEXT | **冗余快照**：行情不可用时仍能显示名称，不出现空白行 |
| `note` | TEXT | 备注（v1 不编辑，预留） |
| `sort_order` | INTEGER NOT NULL DEFAULT 0 | 预留手工排序 |
| `created_at` / `updated_at` | TEXT NOT NULL | 与现有表风格一致，UTC ISO8601 秒精度（沿用 `db.py::_now()`） |

索引：
- **唯一索引** `(user_id, code)` —— 幂等的根本保证，防重复添加、防并发双击。
- 普通索引 `(user_id, sort_order, created_at)` —— 列表查询。

设计说明：
- **`ON DELETE CASCADE` 有效前提**是 `PRAGMA foreign_keys = ON`，`get_conn()` 已在 `db.py:93` 开启，无需额外处理。
- **建表即迁移**：`get_conn()` 每次连接执行 `executescript`，老库升级后新表自动出现、老数据不受影响。**不需要写迁移脚本，也不要改动 `DB_PATH` 逻辑**。
- 建议在服务层设**单用户上限（如 200 条）**，超限返回明确错误，防滥用（对齐 F-28 的额度思路）。
- 是否允许添加"当前无行情"的代码（如未来上市、停牌、退市）→ 建议**允许**，靠 `name` 冗余字段兜底显示（见 §5.4）。

### 3.2 接口设计（8002，FastAPI）

| 方法 | 路径 | 入参 | 返回 | 语义 |
|---|---|---|---|---|
| GET | `/api/watchlist` | — | `{ok, items:[{code,name,note,created_at}], count, limit}` | 列出当前用户自选（按 `sort_order, created_at`） |
| POST | `/api/watchlist/add` | `{code, name?}` | `{ok, added:bool, count}` | **幂等**：已存在返回 `added:false` 而非报错 |
| POST | `/api/watchlist/remove` | `{code}` | `{ok, removed:bool, count}` | **幂等**：不存在返回 `removed:false` |
| POST | `/api/watchlist/order` | `{codes:[...]}` | `{ok, count}` | 重排（v1.5，可延后） |

**为什么不用 RESTful 的 `DELETE /api/watchlist/{code}`** —— 这是一个必须提前知道的硬约束：

> `frontend/server.py` 的请求处理器**只实现了 `do_GET`（`:1581`）与 `do_POST`（`:1752`）两个方法**，全仓**没有** `do_DELETE` / `do_PUT` / `do_PATCH`。任何 DELETE/PUT 请求会在 8000 层直接返回 501，**根本到不了 8002**。
>
> 因此有两条路：
> - **路线 1（推荐 v1）**：用 `POST /api/watchlist/remove` 表达删除语义，**零改动 HTTP 方法层**。
> - **路线 2**：在 `frontend/server.py` 新增 `do_DELETE`（约 10 行）并在其中复用 `_proxy_report`。若选此路，需同步确认 `_proxy_report` 对无 body 请求的处理（`:1711-1714` 仅在 `method == "POST"` 时读 body，DELETE 无 body 可正常工作）。

**鉴权注意（最容易写错的点）**：`_auth_gate` 中间件只做"拦截/放行"，**不把用户对象注入 request**（`api/server.py:263-270` 丢弃了 `get_user_by_session()` 的返回值）。端点内部要拿 `user_id`，**必须自己再取一次**：`_auth_token(req)` → `auth_service.get_user_by_session(token)` → `user["id"]`。`_user_dict`（`auth/service.py:118-125`）确实返回 `id`，可直接使用。

### 3.3 行情拼装接口（8000，静态服务）

新增 `GET /api/watchlist_quotes`：

- **入参**：无（服务端自取当前用户 codes）。
- **内部流程**：① 代理 8002 `/api/watchlist` 取 codes → ② 用 `get_records()`（`:80`）过滤 → ③ 按需排序/分页。
- **返回结构**：**与 `/api/stocks` 完全同构** —— `{updated, total, page, pageSize, stocks:[...]}`（见 `handle_api_stocks` `:148-157`）。

这样设计的原因：`get_records()` 返回的全市场 record 字段（`fetch_stocks.py:217-253`）与 `stock.html::buildRow(d)`（`:254-281`）所需的 `name / code / ind / price / chg / dir / mcap_disp / fcap_disp` **完全一致**。因此自选列表页**可以直接复用 `renderApi()` 与 `buildRow()`，几乎不改渲染代码**，也**不需要任何新的外部数据源请求**。

## 四、与现有系统的交互方式

### 4.1 与静态服务路由的接入点

`frontend/server.py` 的路由是**显式分支 + 前缀匹配**，需在两处接入：

| 位置 | 现有内容 | 需做 |
|---|---|---|
| `do_GET`（`:1581-1695`） | `/api/report` 与 `/api/auth` 分支（`:1672-1681`） | 加 `/api/watchlist` 分支 → 代理到 8002；再加 `/api/watchlist_quotes` 分支 → 本地行情拼装 |
| `do_POST`（`:1752-1763`） | 仅 `/api/report`、`/api/auth`；其余 `405` | 加 `/api/watchlist` 分支 |
| `_proxy_report`（`:1703`） | 名称带 report，但实现是**通用的**（用 `self.path` 转发） | 可直接复用；建议顺手改名或补充注释，避免"名字叫 report 却代理 watchlist"的误解 |

### 4.2 与鉴权链路的交互（双层，且都自动生效）

- **8000 层**：`_PUBLIC_PREFIXES = ("/css/", "/js/", "/api/auth")`（`:55`）+ `_PUBLIC_EXACT`。`/api/watchlist` 不在其中 → 自动判定为非公开路径，`do_GET` 会先走 `_session_ok()`（`:1586`），未登录返回 401 JSON。
- **8002 层**：`_auth_gate`（`api/server.py:263-270`）对 `/api/` 全量拦截（`/api/auth/` 除外）→ `/api/watchlist` 自动受保护。

结论：**两层鉴权都无需改动**。但需知晓 8000 层的 `_session_ok()` 是**同步阻塞内网调用**（timeout 3s，`:1555-1572`），这正是已知性能债（优化清单 T-31），自选页应**一次拿全量 codes**，严禁逐行 N+1。

### 4.3 与行情链路的交互

复用 `get_records()`（`:80-100`）的**交易日内存缓存**：全市场数据一天只拉一次，自选筛选在内存完成，**零额外外部请求**。

同时必须处理它的已知缺陷（这正是此前"股票页空列表"的根因）：`get_records()` 在拉取失败且无旧缓存时返回 `[]`（`:96`），而**失败路径不会写入 `_cache`**（`:97-99` 只在成功时写），但 `fetch_stocks.fetch_all()` 的"每页 3 次失败即 `break` 返回 `[]` 且不抛异常"（`fetch_stocks.py:87-119`）会让**空结果被当成成功写入当日缓存**，导致整日不可自愈。自选页必须显式区分这个状态（见 §5.2）。

### 4.4 与前端页面及状态机的交互

| 交互对象 | 位置 | 要点 |
|---|---|---|
| `CODE` 全局 | `stock_detail.html:328` | 加自选时的代码来源，已做 `[^0-9]` 清洗 |
| 名称来源 | `FALLBACK_DETAIL[code].name`（`:347-354`）或 `/api/stock` 返回 | 写入 `watchlist.name` 快照 |
| 按钮样式 | `.watch`（`:28-29`） | **仅有 hover 态，无选中态** → 需补 `.watch.on` 样式以示"已自选" |
| 行点击冲突 | `stock.html:274-278` | `buildRow` 把**整行**绑定了跳转详情，加星标必须 `stopPropagation()`，否则点星也会跳页 |
| 列表状态快照 | `stock.html:199-200` / `list_state.js` | 快照含 `sort/order/page/q/pageSize/scrollY`；若加"仅看自选"筛选，**必须一并纳入快照**，否则返回列表时筛选丢失 |
| 双渲染路径 | `renderApi` vs `doFallbackRender`（`stock.html:290` / `:220`） | 兜底模式基于 `frontend/data/stocks.json`（**仅 6 条**）；若走方案 B，两条路径都要正确处理自选筛选 |
| 登录跳转 | `frontend/server.py:1590-1592` | 会话过期收 401 时应跳 `/login.html?next=...`，复用现有 `next` 机制 |

### 4.5 与报告链路的关系

**v1 不产生任何交集**：自选只读写 `watchlist` 表，不触碰 `report_types/`、`pipeline/`、`api/tasks.py`，因此**不会影响基本面/概况/行业/板块四类报告的任何现有路径**（符合项目"物理隔离、互不污染"的既有原则）。后续 F-10/F-23 引入时再单向读取自选列表。

## 五、边界情况与潜在风险

### 5.1 幂等与并发

| 场景 | 处理 |
|---|---|
| 重复点击"加自选" | 唯一索引 `(user_id, code)` + 插入用 `INSERT OR IGNORE`；返回 `added:false`，前端按成功处理（不弹错） |
| 快速双击、多标签页同时操作 | 以服务端返回的 `count` 为准回写按钮态；前端可做乐观更新 + 失败回滚 |
| 已加自选后再加 | 幂等，不产生重复行 |
| 取消不存在的自选 | 幂等，`removed:false` |

### 5.2 行情失败 vs 自选为空（**最关键的一条**）

两种"空"必须完全区分，否则会复现此前"股票页空列表"的用户体验事故：

| 情形 | 判据 | 应显示 |
|---|---|---|
| 自选确实为空 | `count == 0` | 空态引导："还没有自选，去个股页添加" |
| 行情源异常 | `count > 0` 但 `stocks == []` | **"行情数据暂不可用，请稍后刷新"**，附重试按钮（**不得显示"未找到匹配……"**） |
| 正常 | 两者均非空 | 列表 |

**禁止**沿用 `stock.html:297` 的 `未找到匹配「」的标的` 文案来兜底这两种情况。建议 8000 侧在响应中显式带一个状态标识（如 `data_status: "ok" / "empty" / "unavailable"`），让前端不做猜测。

同时建议自选页在 `get_records()` 为空时，**降级为逐只调用 `/api/stock?code=`**（走 `push2delay` 单股行情 + `F10` 基本面，是**独立于 clist 的取数通道**，`:326`/`:341`），最多 200 次但只在异常时触发。这是"降级不中断"在自选页的自然延伸。

### 5.3 代码合法性

- 非法格式（非 6 位数字）→ 服务端用 `_code_ok()`（`api/server.py:52`）拒绝，400。
- 合法但当前无行情的代码（停牌/退市/未来上市）→ 建议允许加入，靠 `name` 冗余字段与"行情不可用"标记显示，**不静默隐藏**（静默隐藏会让用户以为数据丢了）。
- 名称快照可能过期（改名、加 ST）→ **读取时优先用行情返回的名称覆盖显示名**，快照仅作行情缺失时的兜底。

### 5.4 其他边界

| 场景 | 处理 |
|---|---|
| 用户账号被删除 | `ON DELETE CASCADE` 自动清理自选 |
| 会话过期（页面久留后点击） | 401 → 跳 `/login.html?next=<当前详情页>` |
| 自选数量超上限 | 明确提示"自选已达上限 N 只"，而非静默失败 |
| 分页 | v1 不分页（自选通常 < 100）。**注意** `handle_api_stocks` 对 `pageSize > 100` 会回落为 6（`:129-130`），复用其分页逻辑时勿踩 |
| 多设备并发 | 以服务端为唯一事实源，前端本地不持久化自选 |

### 5.5 风险清单

| # | 风险 | 影响 | 对策 |
|---|---|---|---|
| R1 | **`auth.db` 安全问题被放大**：该库含真实手机号且**当前被 git 跟踪**（优化清单 T-01 未处理） | 若先做 F-03 再做历史清理，新表数据与旧数据同命 | 先明确 `data/auth.db` 是运行时数据、**绝不入仓**；若已计划清历史，注意新表数据会一并回滚 |
| R2 | **`AUTH_DB_PATH` 口径不一致**：该变量由环境变量控制（`db.py:30`），但 `.env` 的 `AUTH_*` **不经 dotenv 加载**（优化清单 T-06） | 理论上存在两进程读到不同库文件的可能（自选只由 8002 读写，风险较低，但注册与自选必须同库） | 实施前确认 8002 进程实际的 `AUTH_DB_PATH` 与账号注册时一致 |
| R3 | **列表排序缺陷**（顺带发现，需复核）：`handle_api_stocks` 的 `sort_key(r) = r.get(sort)`，`sort` 取值 `mcap/fcap/chg`，而 record 中 `chg` 是**展示字符串**如 `"+1.23%"`，数值字段是 `chg_num`（`fetch_stocks.py:222-223`）；`SORT_FIELDS`（`:68-72`）映射的中文字段名在 record 中并不存在 | 若自选页提供"按涨跌幅排序"，会退化为字符串比较，结果错误 | **自选页排序放在前端做**（数据量小，用 `chg_num`），绕开该缺陷；该缺陷本身建议单独记录修复 |
| R4 | 8000 层 `_session_ok()` 同步阻塞（timeout 3s） | 自选页首屏额外延迟 | 一次取全量 codes，禁止 N+1；后续随 T-31 一起优化 |
| R5 | 双层代理多一跳（浏览器 → 8000 → 8002） | 增加失败面与延迟 | 保持接口最小化（4 个端点），并复用 `_proxy_report` 的 502 友好提示 |
| R6 | 无自动化测试网：`pytest` 不在 `requirements.txt`（优化清单 T-22），已有 11 个用例跑不起来 | 自选接口无回归保护 | 借本功能补齐 pytest 依赖，为自选 CRUD 补最小用例（幂等、鉴权、上限、非法 code），作为后续功能的安全网 |
| R7 | 前端双渲染路径（API / 兜底）不一致 | 走方案 B 时容易只改一路 | 优先方案 A（独立页）；若走 B，两条路径同批改并回归 |

## 六、建议实现步骤与先后顺序

原则：**自下而上、每步可独立验证、每步可独立回滚**。前端入口放最后，避免"页面已上线而后端 404"。

### Step 0 · 决策确认（不含编码）

需先确认 4 件事：
1. API 落点确认为 **8002**（本方案建议）。
2. 删除语义走 **`POST /remove`**（路线 1，零改动）还是新增 `do_DELETE`（路线 2）。
3. 单用户自选上限（建议 200）。
4. 是否允许添加"当前无行情"的代码（建议允许）。
5. 页面形态选 **方案 A（`watchlist.html`）** 还是方案 B。

### Step 1 · 数据层（最小、最先）

- 在 `auth/db.py::SCHEMA_SQL` 追加 `watchlist` 表与 2 个索引。
- 验证：在**已有数据的旧库**上跑一次 `python -m fundamental_agent.auth.db`，确认新表创建成功、`users`/`sessions` 数据完好；确认 `foreign_keys` 生效（删测试用户后其自选被级联清除）。
- 回滚成本：删表即可，无副作用。

### Step 2 · 领域层 + 接口层

- 新增自选仓储（`auth/watchlist.py`）：`list_by_user` / `add` / `remove` / `reorder`，含上限校验与 `INSERT OR IGNORE`。
- `api/schemas.py` 追加请求/响应模型；`api/server.py` 追加 4 个端点（**注意 §3.2 的"中间件不注入 user、需自行取一次"**）。
- 验证（curl 直连 8002，带 Cookie 或 Bearer）：加→查→重复加（`added:false`）→删→重复删（`removed:false`）；不带会话应 401；非法 code 应 400；超上限应明确报错。**此步建议顺带把 pytest 依赖补进 `requirements.txt` 并写最小用例（对应 R6）。**

### Step 3 · 网关层 + 详情页按钮

- `frontend/server.py`：`do_GET`、`do_POST` 各加 `/api/watchlist` 分支（复用 `_proxy_report`）。
- `stock_detail.html`：把 `:1108` 的假实现替换为真实调用——进入页面时查初始状态并回显（需取一次状态，可复用 `GET /api/watchlist` 或新增轻量 `check` 参数）、点击切换、401 时跳登录页 `next` 回来；补 `.watch.on` 选中态样式。
- 验证：加自选 → 刷新页面 → 状态仍为"已自选"；换浏览器/设备登录同账号仍为"已自选"（**这是本功能的核心验收点**）。

### Step 4 · 自选列表页

- 新增 `watchlist.html`：复用 `stock.html` 的行渲染与列表样式（`buildRow` + `renderApi`）。
- `frontend/server.py` 新增 `GET /api/watchlist_quotes`：取 codes → `get_records()` 过滤 → 返回**与 `/api/stocks` 同构**的结构，并带 `data_status` 标识（§5.2）。
- 在 `index.html:30-35` 导航加"我的自选"入口。
- 验证：正常态、空态、行情异常态（可临时断网/清缓存模拟，确认显示"行情暂不可用"而非"未找到"）。

### Step 5 · 打磨与增强（可延后）

- 列表页"仅看自选"开关（方案 B 部分）→ 若做，需把筛选标记纳入 `list_state.js` 快照（`stock.html:199-200`）。
- 取消自选（列表内直接删）、批量删除、手工排序（`sort_order` + `/order` 端点）。
- 备注/标签编辑（`note` 字段已预留）。
- 为后续 F-23/F-24 预留读取接口（只读，不改本期结构）。

### 顺序依赖图

```
Step 0 决策
   ↓
Step 1 数据层 ──→ Step 2 领域+接口 ──→ Step 3 代理+详情页按钮 ──→ Step 4 自选列表页 ──→ Step 5 打磨
                        │                        │
                    （可单独验证）           （核心验收点在此）
```

**关键提醒**：Step 1~3 完成即已实现"自选可持久化"这个**最小可用闭环**（在详情页加、刷新后仍在）。若需要快速见效，Step 1~3 可作为第一批交付，Step 4 的列表页随后跟上。

## 七、验收清单（供实施后逐条核对）

1. 详情页加自选 → 刷新 → 仍为"已自选"。
2. 换设备/浏览器登录同账号 → 状态一致（证明落库而非前端缓存）。
3. 重复点击不产生重复行（查库确认 `watchlist` 唯一约束生效）。
4. 未登录直接请求 `/api/watchlist` → 401（两层都应拦住）。
5. 非法 code（如 `12`、`abcd`）→ 400，且不写库。
6. 自选为空 → 空态引导；行情源异常 → "行情暂不可用"，**绝不显示"未找到匹配「」的标的"**。
7. 自选上限 → 明确错误提示。
8. 删除用户 → 其自选被级联清除。
9. 会话过期后点击按钮 → 跳登录页，登录后回到原详情页。
10. 现有 4 类报告（基本面/概况/行业/板块）与 `stock.html` 既有筛选、`list_state.js` 恢复行为**均无回归**。
