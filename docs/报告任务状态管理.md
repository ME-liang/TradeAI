# 报告生成任务模型与状态隔离（含状态串扰事故复盘）

> 适用：`POST /api/report` 异步任务（概况 / 基本面 / 行业对比 / 板块深度报告）。
> 复盘日期：2026-09-11。**最近更新：2026-09-26（第五节：F-04 任务中心，含 7 条"必须守住的约束"与 5 条明确边界；同日追加第六节：失败任务可手动删除；同日追加第七节：报告库删除与任务状态管理的交界）。**

## 一、任务模型（现状）

| 环节 | 实现 | 文件 |
|---|---|---|
| 任务创建 | `TaskManager.create(code, bk, report_type)` → 12 位 uuid；**仅当 code+bk+report_type 都相同且状态为 PENDING/RUNNING 时复用**（避免同类型重复打接口） | `src/fundamental_agent/api/tasks.py` |
| 任务执行 | 每个任务一个 daemon 线程跑 `_worker` → `run_pipeline(report_type=…)` | `src/fundamental_agent/api/server.py` |
| 状态上报 | worker 经 `tm.update(task_id, stage/progress/status/html_path)` 回写**自己任务**的状态槽；**SUCCESS 时另回填 `report_id`**（持久标识，供 F-04 任务中心下发链接） | 同上 |
| 进度轮询 | `GET /api/report/{task_id}` 返回该任务独立状态（**内存凭证**，见第五节"必须守住的约束"第 1 条） | 同上 |
| 任务列表 | **v2.10 新增**：`TaskManager.list(user_id, active_only, limit)` + `GET /api/tasks`，供**全站**任务中心（F-04）读取本人近 N 条任务 | `api/tasks.py` / `api/server.py` |
| 任务删除 | **v2.11 新增**：`TaskManager.remove(task_id, user_id)` / `remove_many(task_ids, user_id)` + `POST /api/tasks/remove` —— **只允许删终态**（活跃任务拒删并回报 `skipped_active`）、**归属取自会话**、**不碰磁盘产物**（详见第六节） | `api/tasks.py` / `api/server.py` |
| 产物落盘 | `output/reports/{code}/[{report_type}/]{date}/report.html`（**按类型物理隔离**）+ `profile.json` + `meta.json` | `src/fundamental_agent/storage.py` |
| 当日复用 | 同 code+report_type（industry 另加 bk）当日已有 SUCCESS 产物 → 直接复用（`force=true` 跳过）；**复用分支同样要回填 `report_id` 与 `name`**（否则任务中心里这条会"成功但没有链接"） | `api/server.py: _reuse_today` |
| 前端 | 三类报告各自维护 `ovTaskId/fundTaskId/indTaskId` + 独立轮询定时器 + 独立 iframe 面板（**页内形态，切页即失联**）；**v2.10 起另有全局任务中心** `frontend/js/task_center.js`，两种挂载形态（报告库页内联区块 / 其余页面右下角胶囊+抽屉） | `frontend/stock_detail.html` / `frontend/reports.html` / `frontend/js/task_center.js` |

**隔离的三道保障**：①任务标识（tm 去重键）②任务状态槽（按 task_id）③产物路径（按 report_type）。

## 二、事故复盘：概况报告被基本面报告覆盖（2026-09-11，已修复）

### 现象
先点「AI生成公司概况报告」，再点「AI生成基本面分析报告」→ 两份报告同时生成，**概况面板显示的是基本面报告**。

### 根因（唯一根因，已实测复现）
`TaskManager.create` 的**去重键缺少 `report_type`**：

```python
# 修复前
if t.code == code and t.bk == bk and t.status in ("PENDING", "RUNNING"):
    return t          # ← 概况任务 RUNNING 时，基本面请求也命中这里
```

机制链条：

1. 概况任务 A 创建（RUNNING，正在生成概况报告）；
2. 点基本面 → `create_report` 调 `tm.create(code, bk)` → **命中 A 并原样返回**（code/bk 相同、状态 RUNNING），**没有创建新任务**；
3. 但调用方仍以 `report_type=fundamental` **启动了第二个 worker 线程**，并把 **A 的 task_id** 传给它；
4. 两个 worker 并发共用同一个 task_id，交替 `tm.update()` → `stage`/`progress` 交叉，**最终 `html_path` 由后完成的 writer 决定**（实测为基本面路径）；
5. 前端两个面板各自轮询**同一个 task_id** → 概况面板的 iframe 加载到基本面报告（实测两面板 `src` 完全相同，均指向基本面产物）。

补充证据（插桩实测）：两次 POST 返回同一 task_id（`d51a960cd16c`），该任务最终 `html_path` 指向 `…/fundamental/…/report.html`；而磁盘上 `…/overview/…/report.html` 内容仍是正确的概况报告 —— 证明**不是文件互相覆盖，而是任务状态槽被两个 worker 争用 + 前端被指向同一任务**。

### 修复
把 `report_type` 纳入任务标识（三文件小改，无接口破坏）：

| 文件 | 改动 |
|---|---|
| `api/schemas.py` | `TaskStatus` 新增 `report_type: str = ""` |
| `api/tasks.py` | `create(code, bk, report_type)`；去重条件加入 `report_type` 比对 |
| `api/server.py` | 三处 `tm.create(...)` 传入 `report_type`（board / 复用分支 / 常规分支） |

修复后行为：
- `code+bk+report_type` 全同且仍在跑 → 复用（原「避免重复打接口」语义保留）；
- 任一项不同 → 新建独立任务，各自独立状态槽与产物路径。

### 验证（修复后实测）
1. **三类型并发**：POST overview / fundamental / industry 连续提交 → 返回 **3 个互不相同的 task_id**，`report_type` 字段各自正确；
2. **同类型去重仍生效**：重复提交 overview → 返回同一个 task_id（不重复起任务）；
3. **前端真实点击复现转绿**：概况任务 `71ed85cd8dcc` vs 基本面任务 `adbe0e4857f9`（不同），两 iframe src 不同，概况面板内容=概况报告、基本面面板内容=基本面报告，磁盘两份产物内容各自正确；
4. **行业报告单独验证**：`300184 + BK0890` → SUCCESS，落盘 `output/reports/300184/industry/20260911/report.html`。

### 必须守住的约束（写下来，因为每一条都是"静默失效"）

1. **任务中心不得下发 `/api/report/{task_id}/html`**。那是**内存凭证**，8002 一重启链接即失效——这正是 F-06 交付时修掉的缺陷，不能在任务中心里重新引入。下发的一律是 `/api/report/view/{report_id}`。
2. **`report_id` 必须"反推"而非"按今天现算"**。行业对比报告的日期段带 `__{bk}` 后缀（D8 决策），现算会造出指向**不存在目录**的 id（即 N-21 的形状）。`report_id_for_path()` 取的是 `report.html` 的**父目录名**——那是磁盘上真实存在的那个段。
3. **"SUCCESS 出现在任务中心" ⟹ "报告库已能查到"**。这条由 `_worker` 的**语句顺序**保证：**先 `save_report()`，再 `tm.update(status="SUCCESS")`**。因此前端在完成事件里只需**重载列表**，不需要任何搬运动作。**改动 `_worker` 时必须保持这个顺序**。
4. **容量淘汰只动终态任务**。淘汰 PENDING/RUNNING 任务会让 worker 的 `update()` **静默 no-op**（`_tasks.get()` 返回 None 直接 return）→ 前端进度条**永久卡死**，且日志里什么都没有。
5. **排序与淘汰都用 `_tasks` 的字典插入序（= 创建序），不要用 `created_at`**。`created_at` 只有**秒精度**，同一秒内提交多个任务时，"最新在前"与"最旧先淘汰"都会退化为任意顺序（实测表现为两次请求返回的列表顺序不一致）。换 Redis 时必须**显式保留这个顺序契约**。
6. **`user_id` 只能取自会话**，不能从 query/body 取。否则未登录即可读到别人含 `html_path`（磁盘路径）与失败原因的任务列表。
7. **"只动终态"有两个入口，必须逐个守**（v2.11 追加）。第 4 条的**容量淘汰**与用户**主动删除**都会减小 `_tasks`；只在淘汰上守住终态、却在删除上留个后门，等于没守——删掉运行中的任务同样会让 worker 的 `update()` 静默失效、进度条永久卡死。测试断言的是"**拒删 且 拒删后 `update()` 仍生效**"（只断言"任务还在"会漏掉"删掉后又塞回一个幽灵对象"这种退化：列表里看着在，却永远不动）。

### 与前四轮的关系

这是 `docs/产品功能扩展建议清单.md` 里 **F-04** 的交付，也是该清单**首个"按计划做的新功能"**（v2.5 之后连续四轮都是计划外的正确性修复）。它同时**更正了 v2.5 的一条判断**——当时注"F-04 的价值部分被 F-06 覆盖"，实测**不成立**：F-06 覆盖的是"**已经生成完的**产物可查"，F-04 覆盖的是"**正在生成的**过程可见"，两者互补而非替代。

## 六、2026-09-26 追加：失败任务的出口（手动删除）

**问题**：失败任务**不落盘**（没有产物），只活在 `_tasks` 这个进程内字典里，而 `list()` 会一直把它列出来 —— 跑几次参数错误的生成（实测：提交不存在的板块 `BK9999`）就会把「需要处理」区堆满同一行字，**用户没有任何出口**（唯一的消失方式是等 8002 重启）。第五节把"失败"显式暴露进任务中心是对的（报告库看不到它，只能由任务中心兜住），但**漏了配套的关闭动作**：把问题显式暴露出来却没有出口，就变成"暴露之后无处可去"。

**做法**：新增 `POST /api/tasks/remove`（body `{"task_ids": [...]}`，响应 `{ok, deleted, not_found, skipped_active, count}`）；前端在**失败行**与**「成功但定位不到产物」行**各给一个「删除」，「需要处理」多于一条时在区标题给「全部删除」。

**四条不变量**：

1. **只允许删终态**（即上方约束第 7 条）。PENDING/RUNNING 一律拒删并出现在 `skipped_active` 里，**绝不静默少删**（静默少删 = "删除键点了没用"这类无从排查的故障）。
2. **「别人的任务」与「不存在的任务」返回完全相同的响应**（都用 `not_found`，**刻意不引入 `forbidden`**）。一旦区分，本端点就成了他人 task_id 的**存在性探测器**——据此可推断别人正在为哪只票生成什么报告。
3. **删任务 ≠ 删报告**。SUCCESS 的产物仍在报告库（报告库扫磁盘，不看 `_tasks`），本操作只清理任务中心里那条记录。因此**入口只给失败 / 异常行**，「已完成」行不给删除按钮（否则用户会以为自己在删报告）。
4. **前端按回执更新本地列表**：用 `deleted` / `skipped_active` 决定哪几行消失。把点过的 id 无条件抹掉会制造**幽灵条目**——服务端拒删活跃任务、本地却认为删成功了，下一次轮询它又冒出来（比直接报错更难排查）。

**8000 侧：删除用 POST 而非 DELETE**。本侧只有 `do_GET` / `do_POST`（**无 `do_DELETE`**），这与 F-03 的「删除自选用 `POST /api/watchlist/remove` 表达」是同一条路线。**注意：同一个 `/api/tasks` 前缀这次要在 `do_POST` 里再写一遍分支**（v2.10 只写了 GET 侧）——漏配时请求落到 `do_POST` 末行的 `send_error(405)`，页面表现只是**"点了删除没反应"**，405 只在浏览器控制台可见；用 DELETE 更糟，**501**（本侧连方法都没有）。这是 N-23（8000 侧逐前缀硬编码白名单）的第二次命中。

**验证（实测，经 8000 代理与浏览器同一条路径）**：造 2 条真实 `BK9999` 失败任务 → 删 1 条（`deleted=1`，FAILED 2→1，回执 `count` 与列表一致）→ 真实长任务 RUNNING 时尝试删除（`skipped_active` 显式回报，且 **16 秒后该任务 22% → 100% SUCCESS**，证明 `update()` 链路未被破坏）→ 清空失败记录 → 任务 SUCCESS 后 `/api/report/view/300184.fundamental.20260926` 仍 **200 / 109,183 字节**。`tests/test_tasks_api.py` **24 → 34 例**（新增 3 条护栏：活跃拒删且拒删后 `update()` 仍生效 / 跨用户与不存在的响应逐字段相等 / 删除按钮只在终态行渲染）。

### 未做（明确的边界，不是遗漏）

1. **跑中任务不持久化**：`_tasks` 仍是进程内字典，8002 重启后"已完成任务列表"清空（**但报告仍在报告库里可以打开**——这正是第 2 条约束要保证的）。持久化属 **F-27**。
2. **任务取消 / 重试**未做：本轮需求只要求"可见进度 + 自动进库"。
3. **页内面板刷新后不恢复**：`stock_detail.html` / `sector_detail.html` 的 iframe 进度仍是页内状态，刷新后需重新点按钮（任务本身不丢，任务中心仍能看到它在跑）——即上方第三节遗留第 3 条的**原始诉求**。
4. **进度粒度受 pipeline 上报粒度限制**：实测 `22%` 会停留约 17s，因为 `_on_progress` 在长耗时取数段内不再上报。
5. **任务记录可删，但只删终态、且不碰磁盘产物**（v2.11）：删除只清 `_tasks` 里那条记录；SUCCESS 的产物仍在报告库（报告库扫磁盘、不看 `_tasks`），故 UI 只在**失败 / 定位不到产物**的行给入口。不做跨重启的持久删除 —— 任务列表本身是瞬态，持久化属 **F-27**。

### 验证（实测，非推断）

- 真实任务端到端：`POST /api/report`（`300184` fundamental，**17.5s**）→ 提交后**立即可见**（RUNNING 5% 准备数据源）→ 22% 拉取公司概况数据 → SUCCESS 100% → `report_id = 300184.fundamental.20260926`、`view_url = /api/report/view/300184.fundamental.20260926` → 经 8000 代理打开 **200 / 113,138 字节 / 含 "300184"** → **同一请求内报告库已包含**该产物。

## 七、2026-09-26 追加：报告库删除与任务状态管理的交界（F-06 补充交付）

第六节是"**任务**的出口"，本节是"**产物**的出口"（需求原文：「报告库中的报告也需要支持手动删除」）。两者**不是同一件事**：第六节删的是 `_tasks` 里的一行内存记录（产物照旧在报告库），本节删的是磁盘上整个报告目录（`report.html` + `meta.json` + `profile.json`，不可逆）。但它们在**两个点上必须一起想**，否则会各自制造对方的故障。

### 交界点一：删掉报告 = 任务中心里那个链接立即变成死链

第五节约束第 1 条定下了"任务中心下发的必须是 `/api/report/view/{report_id}`"（持久凭证，不是内存 `task_id`）。这在**单独看时是正确的**，但一旦报告可以被删除，同一条链接就有了第二种失效方式：**目录没了，链接还在**。SUCCESS 任务会长期挂在「最近完成」里，点开就是 `404 报告不存在或不属于当前用户` —— 即 **N-21 的形状**（"列表广告了详情拒绝的条目"）在**生命周期后段**的复发。

**做法**：新增 `TaskManager.forget_report_ids(user_id, report_ids)`，`POST /api/report/remove` 在删除成功后调用它，回执里多一个 `tasks_cleared` 字段。

**三条不变量（缺一条就会误删别人的任务记录）**：

1. **只清本人**（`t.user_id != user_id` 直接跳过）——与第五节约束第 6 条同源：归属只能取自会话。
2. **只清终态**（`t.status not in TERMINAL_STATUSES` 跳过）——这是「活跃任务不可删」的**同一个不变量的第三处入口**（前两处：第五节约束第 4 条的容量淘汰、第六节的用户主动删除）。活跃任务**不会**因为它的目标目录被删掉就消失；它由下面的"活跃任务守卫"挡住，根本走不到这一步。
3. **`report_id` 精确相等，且只在真正删成功的那批上清**：清理集合取的是回执里的 `removed_ids`（即 `deleted` 的那些），**`failed` / `not_found` / `skipped_busy` 一律不动** —— 否则会出现"报告没删掉、任务记录却没了"（比死链更糟：用户既看不到报告，也不知道刚才那份跑哪去了）。

### 交界点二：正在为该报告跑任务时，不能删它的目录

删掉一个**正在写**的目录，轻则让 worker 的 `save_report()` 中途失败，重则**写回一个用户以为已经删掉的目录**。故 `delete_reports()` 接收 `busy_keys`，命中则跳过并回报 `skipped_busy`；端点侧由 `TaskManager.active_keys(user_id)` 提供。

**这里刻意"只取 `(主体, 报告类型)` 两元组、不看日期段"**：日期段是 worker 自己算的（行业对比还带 `__{bk}` 后缀，见第五节约束第 2 条与 D8），从任务侧把它复算出来，等于把 `storage` 的路径规则**抄第二份**——正是 N-15 / N-18 / N-23 那一族"同一件事有两个定义处"的老坑。两元组是**保守超集**：宁可多跳过一个其实不冲突的任务，也不要因为路径算错而删掉正在写的目录。板块报告的主体取 `bk`（不是 `code`），与 `create()` 的去重键口径保持一致。

### 前端：不让死链多留一个轮询周期

`frontend/reports.html` 删除成功后派发 `tradeai:report-removed`；`frontend/js/task_center.js` 监听该事件并**立即重拉一次**（不等下一个轮询周期）。任务中心默认空闲时 15s 才轮询（第五节），不主动通知的话，用户刚删完报告就会在同一个页面上看到一个**已经点不开的链接**——两个模块都在报告库页上，观感上像是"删除没生效"。

### 与第五节约束第 3 条的关系（方向相反，不冲突）

约束第 3 条保证的是 **正向**不变量："SUCCESS 出现在任务中心 ⟹ 报告库已能查到"（由"**先 `save_report()`、再 `tm.update(status='SUCCESS')`**"的语句顺序保证）。本节补的是它的**逆向生命周期**："**报告库查不到 ⟹ 任务中心不该再挂着它**"。两条合起来才是完整的：产物存在与链接存在必须**同步出现、同步消失**；只做前半会留下"成功但点不开"的条目，只做后半会留下"报告还在、记录先没"的空洞。

### 未做（明确的边界）

1. **不做"删报告时顺带取消 / 终止活跃任务"**：命中的活跃任务一律 `skipped_busy` 跳过，等它自己跑完。取消任务属 **N-24**（任务无超时 / 无取消）的范畴，不该在删除端点上临时开一个入口。
2. **不做 legacy 共享根的删除**：`user_id` 为空的目录（`output/reports/` 直下）里**别人的产物也在**，删除侧一律 `not_found`、列表项 `deletable=false`。与 N-22「不放宽 `view` 路径边界」同一取向。
3. **不做跨重启的持久清理**：`forget_report_ids` 只清内存 `_tasks`。若 8002 已重启（`_tasks` 本就空），删报告不会、也不需要"回收"任何东西——报告库扫磁盘，不看 `_tasks`。

### 验证（实测，经 8000 代理与浏览器同一条路径）

- 真实落盘产物 → 报告库列出（`deletable=true`）→ 删除（`deleted=1`）→ 原 `view` 链接 **404**、列表不含、磁盘目录与空父目录均消失、**用户根保留**。
- **真实 pipeline 产物**删除后回执 `tasks_cleared=1`，任务中心当场清空、**不留任何死链**。
- **真实 RUNNING 任务期间**删除对应报告 → `skipped_busy` 显式回报，产物仍在，且该任务随后照常跑完。
- legacy 条目 → `not_found`，共享根产物**一份未动**；未登录 → **401**。
- `tests/test_report_remove.py`（**46 例**，新建）含三条专门锁"删不掉"的用例（跨用户 / 不存在 / legacy，每种都同时断言**响应形状**与**磁盘文件仍在**）与源码级护栏（`delete_reports` 必须调 `resolve_report_dir` 且**不出现 `joinpath`**）。真机截图 6 张归档于 `docs/screenshots/F-06-报告库删除/`。
