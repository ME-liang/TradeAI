# 缓存策略与路径说明

> 适用范围：fundamental / overview / industry 三类报告生成共用。
> 盘点日期：2026-09-11（基于当时代码实现，路径如有调整以 `grep -rn "_CACHE\|CACHE_DIR" src/` 为准）。
> 缓存总量现状：约 **42.6 MB**，其中年报 PDF 占 37.7 MB（最大头）。

## 一、总览

缓存分**两个磁盘根目录**（历史设计形成的分裂，见 §五）+ 一组**仅内存**缓存：

| 根目录 | 存放内容 | 特点 |
|---|---|---|
| `src/fundamental_agent/data/_cache/` | 数据层 JSON 小缓存（随代码目录） | 体积小、TTL 短 |
| `data/cache/`（项目根） | 大文件与解析产物 | PDF 体积大头 |
| 进程内存 | 限流器 / 短 TTL 接口缓存 / 熔断状态 | 进程结束即失效 |

**报告产物复用**（不属于缓存，但语义相关）单独列于 §三。

## 二、磁盘缓存明细

### 1. `src/fundamental_agent/data/_cache/` —— 数据层 JSON 缓存

| 子路径 / 文件 | 内容 | TTL | 填充时机 | 备注 |
|---|---|---|---|---|
| `sw_l1_map.json` | 股票代码 → 申万一/三级行业映射（全市场） | 7 天 | 首次构建后写回；不足 1000 条视为残缺会重建（重建有 90s 上限 + 进程内一次性防抖） | 被同业定位/行业归属使用 |
| `fin_indicators/{代码}.json` | 东财「财务分析指标」全量历史（按报告期） | 7 天 | `get_financial_indicators` 首次拉取时 | 空结果不缓存；日期以 ISO 序列化 |
| `fin_indicators/profile_{代码}.json` | 公司画像（名称/行业/市值/上市日期） | 7 天 | `get_company_profile` 首次拉取时 | 仅取到名称才缓存；同业/对标循环逐股调用 |
| `stock_names.json` | 股票代码 → 公司**简称**注册表（单文件全市场累积） | **无过期**（仅作最后兜底，实时源永远优先） | `get_company_profile` 取到名称时（含缓存命中路径） | 抬头修复用：防止东财限流导致报告标题退化为纯代码；名称变更以实时源为准，注册表只补空 |
| `peers_overview/{代码}_{N}.json` | 申万二级同业可比结果（含本公司行与排名） | 24 小时 | `get_industry_peers_overview` 首次计算时 | 空结果不缓存；命中即零成本 |
| `sw_cons/{申万指数代码}.json` | 申万指数成分（index_component_sw） | 7 天 | 成分定位时逐 L2 请求 | 空结果不缓存；**带熔断**：上游连续 2 次失败后本进程内快速失败 |

### 2. `data/cache/` —— 项目根大文件与解析产物

| 子路径 / 文件 | 内容 | TTL | 填充时机 | 备注 |
|---|---|---|---|---|
| `reports/{代码}_{报告名称}.pdf` | 年报/半年报 PDF 原件（PyMuPDF 下载产物） | 永久 | `fetch_annual_report` 下载时 | PDF 本身不变即永久有效；体积大头 |
| `annual_extract/holders_{指纹}.json` | 前十大股东名册（PDF 解析结果） | 跟随 PDF 指纹 | `extract_top_holders` 首次解析时 | 指纹 = 文件名+mtime+size 的 SHA256；空结果不缓存 |
| `annual_extract/actions_{代码}_{指纹}.json` | 分红决策/回购/实控人 | 同上 | `get_corporate_actions` 首次解析时 | 同上 |
| `annual_extract/chain_{代码}_{指纹}.json` | 上下游/客户集中度 | 同上 | `get_business_chain` 首次解析时 | 同上 |
| `statements/{代码}.pkl` | 三大报表 + 画像（pickle） | 7 天 | `build_statements` 时 | 命中则零网络 |

### 3. 熔断与防抖（随缓存行为，需了解）

- **申万成分接口熔断**：`index_component_sw` 连续 2 次失败后，本进程内直接快速失败（不再等单次 ~60s 的超时），交由「未获取」降级；跨进程不记忆。
- **sw_l1_map 重建防抖**：缓存残缺（<1000 条）时全量重建**每进程至多一次**、且有 90s 上限；缺行业公司优先走「证监会大类 → 申万一级」零网络静态映射。
- **LLM provider 当日熔断**：连续失败 ≥3 次的厂商当日跳过（内存态，见 `llm/router.py`）。

## 三、报告产物复用 —— `output/reports/{代码}/{报告类型}/{日期}/`

- 内容：`report.html` + `profile.json` + `meta.json`（27 份，约 2 MB）。
- 行为：同股同类型同日**已有 SUCCESS 产物 → 直接复用**，不再重新生成；前端「重新生成」按钮 / `force=true` 可绕过。
- 注意：`force` 只绕过报告产物复用，**不绕过上表数据缓存**——需强刷数据时按 §四 手动清理。

## 四、仅内存缓存（不落盘，进程结束即失效）

| 缓存 | TTL/策略 | 说明 |
|---|---|---|
| `ttl_cache(3600s)` × 12 处接口 | 1 小时 | 主营构成、质押、新闻、总股本、毛利率、营收(亿)等 |
| `_GDFX_FREE_CACHE` | 当日（进程内） | 东财全市场股东大表按「报告期 → DataFrame」 |
| `throttle(0.25s)` | — | 慢接口全局限流器 |
| LLM 熔断状态 / 申万熔断 / 重建防抖 | 进程内 | 见 §2.3 |

## 五、清理与刷新方法

| 目的 | 操作 | 影响 |
|---|---|---|
| 强刷某公司的财务指标/画像 | 删 `fin_indicators/{代码}.json`、`fin_indicators/profile_{代码}.json` | 仅该公司下次生成重新拉取 |
| 重置公司简称注册表 | 删 `stock_names.json` | 低频（名称变更罕见）；删除后下次生成重新解析 |
| 强刷某公司同业集 | 删 `peers_overview/{代码}_8.json` | 仅该公司 |
| 强刷某公司 PDF 抽取结果 | 删 `annual_extract/` 中该代码相关文件 | 仅该公司（PDF 未变则指纹一致，删后重建一次） |
| 强刷某公司财报 | 删 `statements/{代码}.pkl` | 仅该公司 |
| 全量清空数据缓存 | 删除 `src/fundamental_agent/data/_cache/` 与 `data/cache/`（PDF 可保留） | 所有公司下次生成重新拉取 |
| 同日强制重新生成报告 | 前端「重新生成」按钮（`force=true`） | 只影响报告产物复用，数据缓存仍生效 |

> 清理均为安全操作：缓存会在下次生成时自动重建（仅该次变慢），不会造成数据错误。

## 六、已知不一致与后续建议

1. **两个缓存根目录**：JSON 小缓存随代码目录（`src/.../data/_cache/`），大文件在项目根（`data/cache/`）——迁移部署时两处都要带。可做一次归并统一到 `data/cache/`（带兼容迁移）。
2. **TTL 不统一**：7 天（映射/指标/报表）、24h（同业集）、永久（PDF）——按数据更新频率设计，符合预期；若需统一常量管理可收敛到 `config.yaml`。
3. **sw_l1_map 完整性阈值**：现接受 ≥1000 条的新鲜缓存；上游恢复后建议跑一次 `tools/rebuild_sw_map.py` 把映射补齐到全量（消除缺行业公司的静态映射近似）。
